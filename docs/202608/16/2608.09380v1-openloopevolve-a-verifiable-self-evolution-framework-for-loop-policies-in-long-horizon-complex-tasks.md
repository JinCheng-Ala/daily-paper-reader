## 摘要
长时域复杂任务要求智能体在持续变化的环境中反复观察状态、制定计划、调用工具、验证结果并从失败中恢复。然而，此类控制经验往往局限于单一上下文或固定提示词，难以跨历史轨迹进行积累和复用。本文提出了OpenLoopEvolve（OLE），一种以循环策略（Loop Policy）为中心的自演化框架。OLE将智能体的观察、规划、记忆、行动、验证、恢复、停止和预算控制表示为具有版本和谱系的可移植策略资产，并提供可依据实际需求选择的在线与离线演化模式：在线模式基于持续运行的反馈触发候选生成，而离线模式则从存档轨迹和失败证据中搜索候选策略。两种模式共享一种演化机制，该机制由大语言模型的自主提案、冠军-挑战者（Champion–Challenger）配对评估以及稳健发布组成。在线发布的策略在后续任务边界被激活，利用后续反馈进行监控，并在满足退化条件时回滚至其父版本。在模拟业务基准YC-Bench上，相较于固定的初始循环策略，两种模式均提升了总体任务性能、任务成功率和风险指标。结果表明，将循环策略视为可治理资产能够支持控制经验的积累、比较、发布和复用，并提升智能体在长时域复杂任务上的表现。

## Abstract
Long-horizon complex tasks require agents to repeatedly observe states, formulate plans, invoke tools, verify results, and recover from failures in continuously changing environments. However, such control experience often remains confined to a single context or a fixed prompt, and is difficult to accumulate and reuse across historical traces. This paper presents OpenLoopEvolve (OLE), a self-evolution framework centered on the Loop Policy. OLE represents an agent's observation, planning, memory, action, verification, recovery, stopping, and budget control as portable policy assets with versions and lineages, and provides online and offline evolution modes that can be selected according to practical needs: the online mode triggers candidate generation based on feedback from continuous operation, whereas the offline mode searches for candidate policies from archived traces and failure evidence. Both modes share an evolution mechanism consisting of autonomous proposals by a large language model, Champion--Challenger paired evaluation, and robust release. Policies released online are activated at a subsequent task boundary, monitored using subsequent feedback, and rolled back to their parent versions when degradation conditions are met. On the simulated business benchmark YC-Bench, both modes improve aggregate task performance, task success rate, and risk metrics relative to a fixed initial Loop Policy. The results indicate that treating the Loop Policy as a governable asset can support the accumulation, comparison, release, and reuse of control experience and improve agent performance on long-horizon complex tasks.

## 2. 论文提出的方法论

### 2.1 核心思想

- 将智能体整个执行循环（observation, planning, memory, action, verification, recovery, stopping, budget control）外部化为**Loop Policy**，用八元组表示：  
  `π = ⟨π_obs, π_plan, π_mem, π_act, π_ver, π_rec, π_stop, π_bud⟩`。
- 每个策略版本封装为 **Bundle**：`B_v = ⟨π_v, χ_v, ℓ_v⟩`，包含策略内容、适用条件（χ）、版本谱系（ℓ，记录父版本及演化证据）。
- 定义轨迹 `τ_i = (g_i, π_v(i), H_i, y_i)`，并设计**证据契约**：`E = Φ(D) = {ε_j = (ρ_j, δ_j, u_j, I_j)}`，每条证据包含方向（正/负）、指标变化、目标策略组件、支持轨迹索引。
- 提出统一演化框架：**“证据→候选→配对评估→稳健发布→任务边界激活→监控回滚”**，在线与离线模式共享此边界。

### 2.2 关键技术细节

- **配对评估（Champion–Challenger）**：候选策略与当前冠军策略在同一任务、同一受控运行条件下分别执行，计算绝对和相对价值分数变化：  
  `Δ_{i,j} = q(π_k,j; g_i, z_{i,j}) - q(π_c; g_i, z_{i,j})`，  
  `r_{i,j} = Δ_{i,j} / max(|q(π_c; g_i, z_{i,j})|, ε)`。
- **稳健发布门（Robust Release Gate）**：发布必须同时满足四类约束：收益（benefit）、证据质量（evidence）、尾部风险（tail risk）、资源成本（cost）：  
  `Gate(P_{k,j}, Θ) = accept ⇔ ∏_{α∈{b,e,t,c}} Γ_α(P_{k,j}, Θ_α) = 1`。
- **在线演化模式**（Algorithm 1）：接收可归因轨迹流 → 金丝雀监控（CanaryMonitor）检测退化并回滚 → 满足触发条件后提取证据 → LLM 生成单一候选 Bundle → 配对评估 → 通过门则发布为后继资产，并在**后续任务边界**激活；若后续反馈满足降级条件则回滚至父版本。
- **离线演化模式**（Algorithm 2）：从存档轨迹提取证据 → LLM 生成初始候选集 `C_1` → 多代迭代：对每个候选与 Champion 配对评估 → 累积评估映射 `P_k` → 保留精英集 `F_k`（固定 Champion + 非支配候选）→ LLM 基于评估历史进行变异/重组生成下一代 `C_{k+1}` → 最终从通过门且满足价值最高的候选中选择后继 Champion；若无合格候选则保持原策略。
- **模式差异与统一性**：在线模式基于近期反馈单步更新，离线模式基于存档轨迹多代搜索；两者在候选生成、评估和发布语义上完全一致，且评估历史按模式显式区分（`R = R_on ⊎ R_off`）。

## 7. 优点

- **概念创新**：首次将完整执行环路抽象为可版本化的外部策略资产（Loop Policy + Bundle），统一了观察、规划、记忆、验证、恢复、停止、预算等控制要素，突破了“记忆内容”和“局部技能”的传统视角。
- **框架完备**：设计了“证据—候选生成—配对评估—稳健发布—任务边界激活—回滚”的闭环治理流程，并明确区分了候选生成、验证、发布和激活的边界，防止临时候选干扰正在执行的任务。
- **在线/离线统一**：在线与离线模式共享相同的资产表示和发布语义，分别适用于实时反馈和离线存档轨迹，具有工程灵活性。
- **安全发布机制**：通过 Champion–Challenger 配对评估、四类约束门控（收益、证据质量、尾部风险、资源成本）和降级回滚，降低策略更新引入的尾部风险。
- **实验结果清晰**：在 YC-Bench 上多维度指标一致改善，且报告了 Token 成本，展示了实际部署中的资源权衡。

## 8. 不足与局限

- **实验覆盖有限**：仅在一个模拟业务基准上评估，未涉及 Web、代码、具身等更广泛的长时域任务；任务类型单一，泛化性未知。
- **缺乏消融研究**：未验证各组件（门控、回滚、配对评估、证据契约）的独立贡献，也未比较不同候选数量、代数或模型对结果的影响。
- **依赖 LLM 自主提案**：候选生成质量依赖底层大模型能力；若 LLM 无法提出有效修改，演化可能停滞或退化；未分析这种依赖的鲁棒性。
- **统计验证不足**：仅 3 个种子，未报告置信区间和显著性检验；结果可能存在随机波动。
- **成本问题**：演化验证 Token 开销大（在线 29.82M，离线 24.02M），远超主任务成本；在大规模或高频更新场景下可能不经济。
- **存在偏差风险**：在线模式中，回滚和证据隔离会影响后续演化；离线模式中，存档轨迹的质量和覆盖范围可能引入选择偏差，且 LLM 评估历史可能产生“自我确认”偏差。
- **可迁移性未验证**：论文末尾承认需进一步检验策略跨任务、跨宿主、跨环境的有效性；当前版本谱系和应用性条件仅依赖启发式设计，缺乏在异质环境上的实证支持。
