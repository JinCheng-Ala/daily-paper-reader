## 摘要
随着大语言模型 increasingly 作为自主代理运行，工具路由的可靠评估变得至关重要。当前基准存在三个结构性局限：遵循幂律分布的数据导致罕见场景代表性不足；缺乏对抗性硬负样本掩盖了模型间的性能差异；以及标注流程依赖未经执行验证的LLM判断。本文介绍了PluginEval，一个通过两阶段框架构建的基准，系统性地缓解了这些局限。首先，我们将工具路由表述为三个决策的序列，并将生成与验证分离。LLM提出候选调用，而确定性验证和真实API执行为质量信号提供可靠依据。其次，我们根据功能、意图和边界对每个插件进行分解，以识别触发和排除场景。然后我们生成不同难度级别的查询以填补覆盖空白，包括针对三种失败模式的对抗性负样本，并将它们返回第一阶段进行标注。该过程形成闭环，迭代直到覆盖收敛。评估方面，我们超越聚合准确性。一个锚定于金标注的LLM评判器将失败分类为遗漏调用、虚假调用或参数错误，为每个模型生成详细的错误画像。我们评估了五个模型家族，包括专有模型和开放权重模型，分析它们在不同难度级别和错误类别上的表现，并通过与人工标注的一致性来验证评判器。

## Abstract
Reliable evaluation of tool routing is critical as Large Language Models increasingly operate as autonomous agents. Current benchmarks face three structural limitations: data distributions that follow a power law leave rare scenarios underrepresented; the absence of adversarial hard negatives obscures performance differences across models; and annotation pipelines depend on LLM judgments that have not been validated through execution. In this paper, we introduce PluginEval, a benchmark constructed through a two-stage framework that systematically mitigates these limitations. First, we formulate tool routing as a sequence of three decisions and separate generation from verification. LLMs propose candidate calls, while deterministic validation and real API execution provide reliable quality signals. Second, we decompose each plugin by capability, intent, and boundary to identify trigger and exclusion scenarios. We then generate queries at different difficulty levels to fill coverage gaps, including adversarial negatives targeting three failure modes, and return them to the first stage for annotation. This process creates a closed loop that iterates until coverage converges. For evaluation, we move beyond aggregate accuracy. An LLM judge anchored to gold annotations classifies failures as missed calls, spurious calls, or parameter errors, producing a detailed error profile for each model. We evaluate five model families, including proprietary models and models with open weights, analyze their performance across difficulty levels and error categories, and validate the judge through agreement with human annotations.

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

### 2.1 核心思想：两阶段闭环构建框架（PCCF）

论文提出 **PluginEval Closed-Loop Construction Framework (PCCF)**，将基准构建分为两个相互耦合的阶段：

- **Stage I：执行锚定的集成标注（Execution-Grounded Ensemble Annotation）**
  - 目标是生成可信的标注，核心原则是**生成与验证分离**。
  - 具体流程为：
    1. 多个 LLM 生成器分别提出候选调用（θ ∈ Θ_t ∪ {⊥}），其中 ⊥ 表示放弃调用。
    2. 每条候选先经过**确定性 schema 验证**（字段、类型、必需参数检查）。
    3. 通过后被**参数评估器**（argument evaluator）判断参数是否被查询支持、是否符合插件语义。
    4. 通过后再通过 **MCP（Model Context Protocol）调用真实 API 执行**。
    5. 执行结果由**结果评估器**（result evaluator）判断是否满足用户请求。
  - 每个候选的最终得分为：
    \[
    s_m^{(k)} = \lambda_{\text{arg}} S_{\text{arg}}(z_m^{(k)} | q,t) + \lambda_{\text{out}} S_{\text{out}}(o_m^{(k)} | q,t)
    \]
    - \( S_{\text{arg}} \) 为参数质量分，\( S_{\text{out}} \) 为执行结果满足度，两者取值 [0,1]，权重满足 \( \lambda_{\text{arg}} + \lambda_{\text{out}} = 1 \)。
  - 达到阈值 τ 的候选被接受为金标注；否则将其失败轨迹反馈给生成器进行下一轮细化，最多 R_max 轮。
  - 若 LLM 提议放弃调用（⊥），则不会被执行，而是通过参数评估器判断是否确属信息不足或能力不支持。

- **Stage II：场景驱动的合成与行为校准（Scenario-Grounded Synthesis and Behavioral Calibration）**
  - 根据每个插件的描述，将其分解为：
    - **触发场景（trigger scenarios）**：应调用该插件的请求；
    - **排除场景（exclusion scenarios）**：不需要工具、需要其他插件、或超越目标插件能力的请求。
  - 每个已被验证的样本分配一个主场景用于覆盖核算，其余匹配场景作为辅助标签。
  - 困难度计算：
    - 正样本：按路由所需推理深度分级——0 步为 Easy，1 步为 Medium，≥2 步为 Hard。
    - 负样本：按类型分设目标困难度，分别是领域距离（Type A）、表面相似度（Type B）、能力边界证据（Type C）。
  - 覆盖缺口计算：
    \[
    \Delta_r(u) = \max\{0, b(u) - n_r(u)\}
    \]
    - \( b(u) \) 为目标数量，\( n_r(u) \) 为第 r 轮已验证数量。
  - 仅对缺口 > 0 的场景合成新样本，并返回 Stage I 验证。
  - 对验证通过的负样本，用冻结参考路由模型在 K 次受控运行中评估其行为难度：
    \[
    p_K(x) = \frac{1}{K}\sum_{j=1}^{K} \mathbb{1}\{\hat{y}^{(j)}(x) = y(x)\}
    \]
    - 若 \( p_K(x) = 0 \) 为 Hard，\( 0 < p_K(x) < 1 \) 为 Medium，\( p_K(x) = 1 \) 为 Easy。
    - 若行为难度低于目标难度，则用识别证据强化负样本后再返回验证与校准。
  - 闭环持续迭代，直到覆盖预算满足、连续 L 轮覆盖提升低于阈值或合成预算耗尽。

### 2.2 黄金锚定的细粒度评估框架

- 论文不直接使用字符串匹配，而是提出**黄金锚定的 LLM 判断器（gold-anchored LLM judge）**：
  - 输入为预测调用列表、人工验证过的金标注调用列表和用户查询。
  - 金标注是唯一评估锚点，查询仅用于解释语义等价性，禁止评估器扩展或覆盖金标注。
- 验证分三步：
  1. **工具对齐**：比较预测与金标注中的工具名集合，求交集后仅对交集中的工具对比参数。
  2. **参数过滤**：若某一侧参数为空或缺失，则跳过该对并记录为 skipped。
  3. **语义验证**：由 LLM 判断预测参数与金标注参数是否语义等价，返回二元判定和理由；允许别名、格式差异、数值等价表示，但时间范围等必须严格匹配。
- **查询级评估指标**：
  - 正样本：所有必需工具均被召回且所有参数全部正确才计为 True Positive（TP），否则为 False Negative（FN）。
  - 针对性负样本：调用了目标工具记 FP，否则 TN；全局负样本：调用任意工具即 FP，完全不调用才 TN。
  - 报告查询级 Recall 和 Accuracy：
    - Recall = TP / (TP + FN)
    - Accuracy = (TP + TN) / (TP + FN + TN + FP)
- **错误归因**：将失败分为互斥类别：
  - **Miss recall（漏调用）**：缺少必需的调用；
  - **Parameter error（参数错误）**：参数语义错误，进一步细分为时间错误、缺参、值错误；
  - **Over recall（过度调用）**：负样本上错误调用工具；
  - 另有 judge failure 单独记录。

## 6. 论文的主要结论与发现

- 模型在插件路由上的表现对**评测集难度构成高度敏感**：将 Easy 比例从 0.40 提到 0.60 后，所有模型 Recall 提升 14.73–21.15 个百分点，Accuracy 提升 14.20–22.49 个百分点。
- **难度越高性能崩塌越明显**：Easy 上 Recall 为 74.5%–93.9%，Medium 降至 31.5%–65.3%，Hard 上只有 2.8%–10.8%。
- 模型排序在不同基准上并不一致：Claude Opus 4.6 在 PluginEval 与 BFCL 上第一，Gemini 3.1 Pro 在 APIBench 和 NexusRaven 上第一；DeepSeek-V4-Pro 在 PluginEval 上超过 GPT-5.4，但在 APIBench/NexusRaven 上落后。
- 聚合指标会掩盖错误结构：GPT-5.4 参数错误率最低，但漏调用和过度调用极高，导致整体性能偏低；Claude 召回强但弃权弱；Gemini 错误画像最均衡。
- **时间错误是参数错误中占比最高的子类型**（7.96%–10.41%），是所有模型共享的弱点。
- 人工审计证明：
  - 参考标注整体有效率为 96.33%–96.67%；
  - judge 与三位评审员的观察一致率为 94.33%–97.00%，Cohen's κ 为 0.9221–0.9585。
- 消融验证了 PCCF 各组件的重要性：内容验证防止无关但可执行的调用混入，迭代校准提高有效产出，闭环合成显著提升覆盖率和难度控制，BoN 采样改善生成稳定性。

- **中文唯一性**：主要用于中文查询，是否适用其他语言未见分析，多语言通用性未验证。
- **正负样本不平衡**：2,500 正 vs 500 负，负样本占比小，可能导致评测对“过度调用”的统计效力不足。
- **难度分布主观性**：虽然用参考路由行为校准难度，但参考路由本身是特定模型，难度标签对其他模型未必适配。
- **语义等价判断边界**：LLM judge 在判断参数语义等价时仍可能受 prompt、模型内部偏差影响；尽管人工审计显示一致性高，但参数错误类别的确认率最低（88%–93%）表明该类别仍存在模糊空间。
- **跨基准比较的可比性存疑**：不同基准的任务格式、评价粒度、样本分布差异大，直接比较模型排序可能受基准特有因素干扰。
- **未发布可复现细节**：如生成器的具体模型、合成查询的具体 prompt、MCP 执行环境、数据筛选条件等细节有限，阻碍完全复现。
