## 摘要
智能体基准测试通常只评估最终答案，即使智能体运行在具有状态的运行时上。我们认为这未能充分界定被评估的对象：适当的单元是声明的模型加运行时配置，其故障可能发生在证据获取、运行时路由、安全边界或重复执行中。我们提出了ClawProBench，一个轨迹感知的基准测试，用于在OpenClaw上实例化的运行时原生智能体评估。OpenClaw是一个实时智能体运行时，具有工作区工具和用于浏览、记忆、消息、调度、技能和子代理的原生界面。ClawProBench定义了两个轨道：一个包含102个场景的完整配置，具有实时工作区和原生运行时路由任务；以及一个冻结的68个场景保留集，具有封闭世界JSON输出契约，用于稳健排序。试验通过安全门控公式从执行轨迹中评分，该公式结合了正确性、过程质量和效率，并保留失败证据以供审计。我们的匿名工件包括基准定义、评分代码、清单和清理后的轨迹。我们在完整配置上评估了68个配置，在保留集上评估了37个。最高安全门控平均轨迹得分为0.7671。原生运行时任务的表现不如工作区实时任务（0.5238对0.6415）。在保留集上，pass@k-any优于严格三次试验通过（0.6638对0.2890），而完整配置和保留集的排名显示出弱相关性（Spearman 0.1300）。纯粹基于正确性的排名与过程感知、安全门控和严格通过视图存在显著差异。最终答案排行榜可能隐藏原生界面的弱点、一次性成功和轨迹局部的智能体失败模式。

## Abstract
Agent benchmarks often evaluate only final answers even when agents run on stateful runtimes. We argue this under-specifies what is being evaluated: the proper unit is a declared model-plus-runtime configuration whose failures can occur in evidence acquisition, runtime routing, safety boundaries, or repeated execution. We present ClawProBench, a trace-aware benchmark for runtime-native agent evaluation instantiated on OpenClaw, a live agent runtime with workspace tools and native surfaces for browsing, memory, messaging, scheduling, skills, and subagents. ClawProBench defines two tracks: a 102-scenario full profile with live workspace and native-runtime routing tasks, and a frozen 68-scenario holdout with closed-world JSON output contracts for robust ranking. Trials are scored from execution traces via a safety-gated formula combining correctness, process quality, and efficiency, preserving failure evidence for audit. Our anonymous artifact includes benchmark definitions, scoring code, manifests and sanitized traces. We evaluate 68 configurations on the full profile and 37 on holdout. The top safety-gated average trace score is 0.7671. Native-runtime tasks underperform workspace-live tasks (0.5238 vs. 0.6415). On holdout, pass@k-any outperforms strict three-trial pass (0.6638 vs. 0.2890), while full-profile and holdout rankings show weak alignment (Spearman 0.1300). Rankings based purely on correctness differ substantially from process-aware, safety-gated and strict-pass views. Final-answer leaderboards may hide native-surface weaknesses, one-off successes and trace-local agent failure modes.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：现有智能体（Agent）基准大多只评估“最终答案”，即使智能体运行在具有状态的（stateful）运行时上。一个正确的最终输出仍然可能在操作层面是失败的——例如使用了错误的运行时表面（native surface）、跳过了必要证据、违反了审批边界、浪费性地重试，或没有留下可供用户与审计者检查的轨迹（trace）。
- **背景与动机**：大语言模型（LLM）正越来越多地被评估为“通过运行时与环境交互的智能体”，而非仅仅回答提示的模型。Web、桌面、工作区、工具调用等基准已覆盖了部分空间，但现有基准未充分测量“模型—运行时—轨迹”构成的完整系统，即：一个声明的智能体配置（declared model-plus-runtime configuration）能否在可审计协议下协调原生运行时表面，同时保持可靠性、状态与过程证据。
- **总体含义**：只排名最终答案会隐藏原生表面弱点、一次性的偶发成功、状态差异以及轨迹局部的失败模式。因此，评估单元应当是“声明的模型加运行时配置”，而非独立的模型智能。

## 2. 论文提出的方法论

- **核心思想**：提出 CLAW PRO BENCH，一个轨迹感知（trace-aware）基准，用于“声明的模型加运行时配置”的联合诊断。每个试验从执行轨迹中评分，而非仅看最终输出；并保留失败检查证据、状态标签和发布哈希，以支持审计与可复现性。
- **两条轨道**：
  - **完整动态画像（Full Live Profile）**：102 个活跃场景，含 66 个工作区实时任务与 36 个 OpenClaw 原生任务（覆盖 skills、browser、memory、message、sessions、directory、cron、agent delegation 共 8 类原生表面）；按 6 个能力维度划分：约束、错误恢复、规划、安全、综合、工具使用；难度偏向硬/专家级（91/102）。
  - **冻结现实保留集（Frozen Realistic Holdout）**：68 个工作区风格、封闭世界 JSON 输出契约的离线场景，通过稳定选择器 `realistic-holdout-68-20260511` 固定，经六模型面板校准与剪枝后冻结，用于重复试验可靠性与固定契约跨运行时比较。
- **运行时适配契约（Runtime Adaptation Contract）**：跨运行时评估通过 8 层契约保持语义一致：场景身份与初始工作区、模型身份、端状态模式、规范化轨迹事件、预期证据与工具元数据、工件后置条件、安全边界标签、确定性检查器/评分接口，以及三试验状态报告；并绑定运行时版本、适配器版本、哈希与执行策略。
- **评分公式**：
  \[
  S_{trial} = G_{safety}\,(0.65\,C + 0.35\,P)\,(1 - E)
  \]
  - \(C\)：端状态与工件正确性检查的得分比率；
  - \(P\)：过程质量（必需工具集适当性、有序子序列覆盖、冗余步骤控制或自定义评分规则）；
  - \(E\)：相对最优步数估计的额外工具调用惩罚（默认上限 0.30）；
  - \(G_{safety}\)：严重性感知的非补偿性安全门（无安全失败为 1.0，轻微 0.7，一次重大 0.2，多次重大或严重为 0）。
  - 过程评分允许多种替代路线，不要求轨迹完全一致；但“缺少证据”和“原生表面绕过”（例如仅在文本中模拟发送消息而非真正调用表面）被视为实质性过程失败。
- **聚合计分层级**：每场景三试验得分先平均 → 场景均值按难度权重（易到专家为 1/2/4/8）在能力维度内加权平均 → 6 个维度以固定权重（工具使用与规划各 0.20，其余各 0.15）合成“总体”与“能力”得分。
- **状态语义**：区分干净基线运行、重跑后干净、未解决执行失败三类状态，避免将基础设施故障与模型行为混合。

- **充分性与客观性评价**：
  - 多维度交叉验证较充分：包含非饱和诊断、状态敏感性、分母敏感性、聚合敏感性（best/mean/median/earliest/latest）、bootstrap 区间、C/P 权重消融和公式消融。
  - 公平性考量：采用报告级自举、tie-aware 平均秩、正分过滤与完整分母双重视图，避免单一分数误读；明确指出跨轨道相关性不确定度大（Spearman 0.1754，95% CI [−0.23, 0.54]），不支持精确排序结论。
  - 局限：保留集是“校准的选择器冻结”而非永久不可见的私有测试集，公开发布后存在过拟合风险；原生—工作区差距虽经简单分层仍为正，但无法排除检查器密度、输出格式等混淆因素；失败分类基于自动分组，非独立人工标注，仅作为审计优先级而非最终流行率估计。

## 6. 论文的主要结论与发现

- **非饱和**：当前最强完整画像得分为 0.7671，top-5 差距 0.0661，模型仍有区分空间。
- **原生表面更困难**：原生场景平均 0.5238 明显低于工作区实时场景 0.6415；在困难/专家层、难度分层、维度分层等简单分层下差距仍 >0.10。
- **重复试验差距显著**：保留集上 pass@k-any 均值 0.6638，而严格三试验通过仅 0.2890——“能解一次”远易于“稳定解三次”。
- **跨轨道排序弱且不确定**：完整画像与保留集 Spearman 仅 0.1754（CI 跨零），而完整画像与核心切片、原生切片中等对齐（约 0.76），说明保留集提供了高不确定性但非冗余的排序诊断。
- **评分视图不可互换**：纯正确性均值排序与官方综合排序 Spearman 0.8060（66 行），最大名次位移 46；严格通过视图与综合视图亦有差异。
- **运行时版本与跨框架敏感性**：
  - 同一模型跨 4 个 OpenClaw 发布版本的最大聚合分差约 0.052，严格 3/3 通过最多差 14.7 个百分点；
  - 同一模型跨 OpenClaw/IronClaw/NanoClaw 的最大聚合分差 0.0716（qwen3.6-plus），严格通过差最多 19.1 个百分点（deepseek-v4-flash）；没有一个框架在所有模型上占优；
  - 所有 3,264 + 2,448 条试验记录均报告执行成功状态，表明差异不是基础设施失败造成的。
- **失败模式异质**：低位得分主要由结构化/精确约束失败（10,718 失败检查）、证据缺失（6,674）、审批/时间/权限约束（6,357）、工具或运行时路由（6,115）、恢复/幂等（3,763）、安全/披露边界（3,710）等不同机制驱动。

## 7. 优点

- **联合诊断设计**：不是又一个“更大排行榜”，而是将原生表面覆盖、过程评分、安全门、状态语义、重复试验、冻结保留集与跨运行时适配契约整合为对“每个声明配置”的多视角诊断。
- **可审计与可复现**：场景/检查器/结果清单均有 SHA-256 哈希、冻结选择器、发布清单、失败检查证据、行来源模式与重跑策略，使基准具备很强的审计链。
- **评分政策的透明性与稳健性**：明确声明权重为“正确性多数”政策而非拟合人类偏好；提供公式消融（0.50/0.50 与 0.80/0.20 对比 0.65/0.35 基线 Spearman ≥0.96）、安全门组件诊断、效率惩罚与预效率能力分分开报告。
- **对“过度简化排名”的审慎态度**：论文主动报告宽 bootstrap 区间、状态过滤对比、正分过滤与全分母双视图，避免对跨轨道排序关系下强结论。
- **跨运行时契约的实践验证**：用 IronClaw 与 NanoClaw 在相同工作区契约上完成实际适配与评估，而非仅声称可移植。

## 8. 不足与局限

- **评估对象不是纯模型能力**：分数属于“模型加运行时”配置，不能外推为独立于框架的模型智能；论文明确承认此点，但读者若只看分数仍易误读。
- **跨框架对比不隔离单一机制**：OpenClaw、IronClaw、NanoClaw 在包装器、工具模式、路由、安全层上共同变化，只能作为配置级证据，不能做单组件因果消融。
- **覆盖面有限**：任务领域、语言、模型访问路径、提供商配置有限；原生完整画像仅限 OpenClaw，跨运行时证据仅覆盖 4 个模型与 3 个框架在工作区保留集上。
- **冻结保留集并非永久私有**：公开场景虽提升可复现性，但也增加过拟合与数据污染风险；未来需要分批发布、延迟发布或轮换场景，并记录暴露标签。
- **统计不确定度高**：保留集仅 37 个干净条目，共享模型 29 个；跨轨道相关区间跨零，模型之间的细微排序差异需要更多干净重跑或更大冻结面板才能支持明确排序。
- **原生差距存在混淆因素**：原生与工作区任务可能在检查器密度、输出格式与措辞上有系统性差异，论文未能完全排除，只能通过分层分析提供非因果诊断。
- **失败分类的局限**：轨迹失败分类由失败检查详情自动分组，缺乏独立人工标注验证，只能作为审计优先级而非最终流行率。
- **成本与隐私披露约束**：API 成本数据依赖公共排行榜文件，零成本占位符与提供商价格表不完整；发布时需要持续执行凭证/路径扫描与红action政策。
