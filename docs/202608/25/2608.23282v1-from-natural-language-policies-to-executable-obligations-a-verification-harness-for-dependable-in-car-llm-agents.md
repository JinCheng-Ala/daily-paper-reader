## 摘要
部署在车辆中的大语言模型（LLM）智能体必须在每一轮操作中满足书面操作策略：单个幻觉标识符、遗漏的强制副作用或过早的完成声明都会导致任务失败。我们提出AgentGuardUtil，这是我们参加CAR-bench Track 1的参赛方案，它将AI规划器（LLM）视为一个在基于事实的验证与修订循环中可能出错的提议者。其核心创新是一个运行时策略编译器：每条对话附带的自然语言策略被编译（每个策略仅编译一次）为类型化的机器可检查规则，其中一部分规则具有可执行形式。一个确定性的义务引擎根据实时的工具结果和草稿本身模拟的写后状态来解释这些规则，发出带有计算参数而非自然语言提醒的精确补救调用。围绕该引擎，25个确定性门控（标识符来源、模式与枚举有效性、先收集后行动、确认及未来时间协议）和一个LLM评审器产生分层发现，驱动一个针对pass k指标调整的有界修订循环。

## Abstract
Large Language Models (LLMs) agents deployed in vehicles must satisfy a written operating policy on every turn: a single hallucinated identifier, omitted mandatory side-effect, or premature completion claim fails the task. We present AgentGuardUtil, our entry to CAR-bench Track~1, which treats the AI planer (LLM) as a fallible proposer inside a grounded verify-and-revise loop. Its core novelty is a runtime policy compiler: the natural-language policy shipped with each conversation is compiled, once per policy, into typed machine-checkable rules, a subset of which receive an executable form. A deterministic obligation engine interprets these rules against live tool results and the simulated post-write state of the draft itself, emitting the exact remedial calls with computed arguments rather than natural-language reminders. Around this engine, 25 deterministic gates (identifier provenance, schema and enum validity, gather-before-act, confirmation and future-time protocols) and an LLM critic produce tiered findings that drive a bounded revision loop tuned for the pass k metric.

### 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：车载环境中部署的 LLM 智能体（如语音助手控制车窗、空调、导航等）必须在每一轮交互中都严格遵守制造商设定的自然语言操作策略。任何单个失误——例如幻觉出一个系统中不存在的标识符、遗漏一项强制副作用（如开空调时未关窗）、或过早宣称任务完成——都会直接导致任务失败，甚至可能引发安全事故（如误读限速导致碰撞）。
- **研究背景**：当前 AI 智能体的评估环境与真实部署条件存在显著差异。真实场景下，用户请求常不完整或含糊不清，工具可能不可用，且存在必须先满足的前置条件、强制副作用、确认要求等策略约束。CAR-bench 基准正是为了捕捉这些部署挑战，涵盖歧义消解（disambiguation）、幻觉拒绝（hallucination拒绝）与策略合规执行（base）三个任务类别。
- **整体含义**：本文的立场很明确：LLM 本身不可被信任，必须将其视为"有能力但会犯错"的提议者，由确定性的代码化验证框架来承担最终保证。核心思路是将可靠性从"模型不犯错"转移到"代码能纠错"，通过确定性的运行时验证把策略合规性、数据 grounded 性和交互协议从模型的概率性输出中剥离出来。

### 2. 方法论：核心思想、关键技术细节与算法流程

#### 2.1 核心思想：学生-教师（Student-Teacher）分解 + 假设-保证（Assume-Guarantee）规约

- **学生（Student）**：LLM 仅负责提出草稿动作（draft action），即候选回复（口语回复 + 工具调用），该草稿在通过验证前既不会展示给驾驶员，也不会执行。
- **教师（Teacher）**：验证框架（AgentGuardUtil）对每份草稿进行审查，返回具体的分层发现（findings），并重新验证修订后的草稿。
- **假设-保证规约**：验证框架只假设学生"有能力但可犯错"，而保证（策略合规、数据 grounded、协议遵守）由从对话自身产物（策略文本、工具模式、观察数据）编译出的确定性检查来承担，独立于学生行为。

#### 2.2 运行时策略编译器（Runtime Policy Compiler，§2.2）

- 在每段对话的第一轮，将自然语言策略文本 Π 编译为类型化规则集 R。每条规则 `r = ⟨id, κ, Tr, ρ⟩` 包含类型 κ（前置条件、自动动作、确认、禁止、披露、约束、选择）、绑定到工具清单的触发器工具集 Tr、以及命令式要求 ρ。
- 复合条款被拆分为原子规则（一个条件、一个补救措施）。
- 第二轮聚焦转换将状态条件规则转化为可执行形式：

```
er = g, φ, ◁, v, ω(x)
```

其中：
  - `g`：读取工具（read tool），获取环境状态；
  - `φ`：字段名模式（含一个通配符）；
  - `◁`：比较运算符（如 >, <, =, ∋ 等）；
  - `v`：阈值；
  - `ω(x) = ⟨u, β(x)⟩`：义务模板，将匹配的项 x 绑定到工具 u 的参数中。
- **安全设计**：编译器看到真实的工具签名，若某义务的参数无法验证则丢弃该规则（退化为咨询级别）。引擎只会增加精度，绝不会强制执行无效调用。

**示例**：策略"当空调设为ON时，若窗户打开超过20%则自动关闭所有窗户"，经编译后得到可执行规则：

```
e011 = get vehicle window positions, window* position, >, 20,
        open close window(⟨item⟩, 0)
```

#### 2.3 可执行义务引擎（Deterministic Obligation Engine，§2.3）

回答了核心问题：给定智能体已观察到的一切和现在提议的动作，策略还要求哪些进一步的动作？分三步：

- **Step 1：估算动作后的环境状态**。设 σ_g 为工具 g 最近返回的观察，w₁..wₘ 为该观察之后已执行的动作，W_a 为草稿提议的动作。引擎按顺序应用这些动作，得到投影状态 `σ̂ = π(σg; w1..m · Wa)`。效果可预测的动作被**模拟**（受影响变量设为动作参数值，ALL 类参数影响所有匹配变量）；效果不可预测或失败的动作将相关变量标记为"未知"。
- **Step 2：计算缺失动作**。规则处于激活状态的条件是：其触发器工具已被使用或出现在草稿中（R▷ = {r : Tr ∩ (Wh ∪ Wa) ≠ ∅}）。

```
Ω(a, h) = ⋃_{r∈R▷} { ω(x) : φ ∼ x, σ̂(x) ◁ v } \ (Eh ∪ Aa)
```

  即：对每条激活规则，对投影值违反条件的每个实体 x 填充动作模板 ω(x)，然后移除已执行（Eh）和草稿中已含（Aa）的动作，剩余集合 Ω 就是智能体仍欠的动作。
- **Step 3：匹配预期粒度**。若所有实体均违规且工具接受 ALL 类参数，则合并为集体动作（符合基准对中间状态的评分粒度）。镜像检查标记多余动作：条件豁免实体的动作，或仅部分实体合格时却用了集体动作。
- **输出**：每条发现附带可立即执行的动作和观察证据（如 `window driver position = 25 > 20`），学生只需转录修正，无需回忆策略。

#### 2.4 分层验证与方差控制（Tiered Verification，§2.4）

- **25 个确定性门控**围绕义务引擎，每个门控检查一个协议，包括：
  - **标识符来源门**：草稿工具调用中的每个不透明标识符必须在先前观察结果中出现过，否则阻止——确定性反幻觉检查；
  - **模式有效性门**：每个参数必须在工具声明类型和枚举值内；
  - **先收集后行动门**：规则依赖的观察条件未被获取时，先要求只读工具调用；
  - **确认协议门**：策略要求用户同意的调用，必须找到用户先前明确肯定的意图问题；
  - **完成声明门**：回复中宣称已执行的动作必须实际执行或在草稿中；
  - **拒绝前读取门**：告诉用户不能做某事时，必须已做过相关只读调用；
  - **未来条件门**：涉及未来时刻的请求（如"到达时是否还营业"），必须用当时的数据回答，而非当前时刻的过滤数据。
- **分层发现机制**：硬发现（hard findings）确定成立，直接触发修订，不过经 LLM 评审器；咨询候选（advisory candidates）由 LLM 评审器批量确认或丢弃，但评审器**不能新增发现、不能推翻硬发现**。
- **振荡阀**：丢弃那些重新要求学生已修订掉的动作集的发现，并放宽收集门，防止门控之间来回拉锯耗尽修订轮次。
- **有界修订循环**：每轮最多 R 次修订，修订后若有硬发现则执行 REVISE_esc（安全网，单独对确定性发现做最后一次修订，可选更强升级模型），最后 SANITIZE 清除无法语音播报的标记。

**关键架构流程（Algorithm 1：VERIFIED TURN）**：
1. 首轮编译策略为可执行规则（按策略哈希缓存）；
2. EXTRACT_ASKS 扫描新用户消息，将明确请求加入待办清单 L；
3. 学生提议草稿 a（若启用投票则 MODAL VOTE 采样 n 次取多数，即 self-consistency）；
4. 进入最多 R 轮的验证-修订循环，每轮执行 Fhard ∪ CRITIC(Fadv)；
5. 空发现则退出，否则 REVISE 注入发现后重新验证；
6. 修订后仍有硬发现则运行 REVISE_esc 安全网；
7. SANITIZE 后释放：验证过的工具调用到达环境，净化的回复到达模拟驾驶员。

### 3. 实验设计：数据集、基准与对比方法

- **基准**：CAR-bench Track 1（官方隐藏测试集）。CAR-bench 评估车载领域 LLM 智能体在真实世界不确定性下的一致性和局限感知能力，覆盖三个类别：base（策略合规执行）、hallucination（拒绝不可用能力）、disambiguation（歧义消解），使用环境状态、工具执行、策略合规和任务终止的**合取成功标准**。
- **具体设置**：组织者隐藏集 30 个任务（每类 10 个），3 个独立试验（trials）为一组。
- **主要指标**：
  - **Pass 1**：单次尝试成功率；
  - **Pass@3**：三次中至少一次成功的任务比例；
  - **Pass 3**：三次全部成功的任务比例（主指标）。
- **对比方法**：组织者基线（80k token 量级的普通 prompt）。
- **学生模型**：Claude Opus 4.8。
- **参赛名次**：21 支队伍中 Pass 3 排名第 9-11 位。

### 6. 主要结论与发现

- **总体效果**：在总成绩上全面超过组织者基线：Pass 3 提升 3.3 个百分点（50.0→53.3），Pass@3 提升 13.3 个百分点（60.0→76.7），Pass 1 提升 6.7 个百分点（60.0→66.7）。
- **类别差异明显**：
  - **Hallucination（最佳）**：Pass 3 达 70.0（基线未给出但总分类差距最大），Pass@3 达 100。原因在于该类检查是简单事实（标识符是否出现过、参数是否符合模式），可由代码确定性判定，对幻觉具有强抑制能力。
  - **Base**：Pass 3 为 50.0，Pass@3 为 60.0。策略合规检查有效但覆盖取决于已编译规则的数量。
  - **Disambiguation（最弱）**：Pass 3 仅 40.0，Pass@3 为 80.0。代码能检查"用户是否确认过"，但无法判断"代理是否应该询问"，这部分依赖 LLM 评审器的判断，而评审器并不总是正确。
- **关键瓶颈**：Pass@3（76.7）与 Pass 3（53.3）之间 23.4 个百分点的差距，来自 8 个任务在部分试验中成功但未全部成功。系统检查本身是稳定的（确定性门控），但学生模型每次产生不同草稿，且未覆盖策略时无检查可触发。**提升 Pass 3 的核心路径是将更多策略编译为可执行规则**。
- **成本结论**：验证框架显著增加 token 和延迟开销，且开销增加不一定带来同比例的分数提升。

### 7. 优点

- **核心创新清晰且有力**：将自然语言策略编译为类型化可执行规则，关键判断从模型移入代码，模型"无法绕过"确定性检查。这是对 LLM 幻觉问题的结构性回应，而非单纯提示工程。
- **精确补救而非模糊提醒**：义务引擎不是告诉学生"你违反了策略"，而是给出带计算参数的立即可执行工具调用（如 `open close window(DRIVER, 0)`），附带证据（`window driver position = 25 > 20`），大幅降低学生出错的自由度。
- **投影状态评估**：对草稿自身写入进行模拟再评估策略，能捕获"草稿自己会造成违规"的缺陷，这是普通回顾式检查做不到的。
- **分层发现机制设计精巧**：硬发现与咨询候选分离，LLM 评审器只能过滤已生成的候选，不能新增、不能推翻硬发现——"坏样本最多丢失一个咨询发现，不会导致虚假修正或压制硬发现"，保证劣化是优雅的而非反向的。
- **失败安全设计**：门控内部错误时贡献为空集（不会阻塞合法草稿）；无法验证参数的规则退化为咨询级别（不会强制非法调用）。
- **工程细节完整**：振荡阀防止门控间无限循环；安全网 REVISE_esc 处理修订引发新缺陷；按策略哈希缓存编译结果。
- **简洁而有效的学生-教师架构**：将系统设计与组合验证的假设-保证规约建立联系，具备明确的形式化基础。

### 8. 不足与局限

- **实验规模有限**：30 个任务、每类 10 个、单一模型（Claude Opus 4.8）、一组试验，统计功效不足。无消融实验量化 25 个门控的各自贡献。
- **无消融与敏感性分析**：没有报告不同修订轮数 R、投票次数 n、评审器温度等超参数的影响，也不清楚对较弱/较强基础模型的适配效果。
- **Disambiguation 类别薄弱**：设计上承认代码无法判断"是否应该提问"，依赖 LLM 评审器，结果是该类别仅 40% Pass 3。这是架构上的固有短板，而非偶然。
- **成本开销显著**：4.4 倍 token、6 倍时间，对车载实时场景（语音助手需要秒级响应）是实际部署障碍。文章没有讨论优化策略（如缓存检查结果、异步验证、更小的评审模型）。
- **策略覆盖依赖人工/LLM 编译质量**：规则只覆盖编译出的部分；未覆盖的策略领域完全没有检查保护（文章承认"checks are silent when no compiled rule covers the task"）。
- **未讨论安全性边界**：文中的"安全保障"是策略合规，但没有讨论恶意用户提示注入、对抗性工具输出、或策略本身冲突时如何裁决。
