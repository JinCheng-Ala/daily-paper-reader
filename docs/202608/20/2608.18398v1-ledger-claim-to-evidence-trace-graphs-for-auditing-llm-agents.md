## 摘要
大语言模型（LLM）智能体现在能够执行涉及复杂工具使用、代码执行、文件编辑和生成工件的长时程技术工作流。随着智能体更快地完成更多工作，生产力瓶颈从产生输出转向审计这些输出是否正确且值得信赖。智能体可观测性系统使细粒度的执行事件可见，但仅靠可见性仍让审查者需要重建哪些动作、工件和验证步骤对特定结论是重要的。我们提出LEDGER——用于执行审查的分层证据与决策图，这是一种在观测到的智能体会话上构建分层追踪图的追踪与审查系统。LEDGER保留追踪记录，同时将其分组为证据节点和工作流节点，将工件表示为证据锚点，并添加连接声明到支持动作、工件和检查的带类型语义边。通过数据分析和编码示例，我们展示了生成的追踪如何暴露工作流决策、工件血缘、修复步骤、验证覆盖范围和面向证据审计的声明支持路径。

## Abstract
Large language model (LLM) agents can now carry out long-horizon technical workflows involving complex tool use, code execution, file edits, and generated artifacts. As agents do more work faster, the productivity bottleneck shifts from producing outputs to auditing whether those outputs are correct and trustworthy. Agent observability systems make fine-grained execution events visible, but visibility alone still leaves reviewers to reconstruct which actions, artifacts, and validation steps matter for a particular conclusion. We introduce LEDGER - Layered Evidence and Decision Graphs for Execution Review, a tracing and review system that builds layered trace graphs over observed agent sessions. LEDGER preserves Trace Records while grouping them into Evidence Nodes and Workflow Nodes, representing artifacts as evidence anchors, and adding typed semantic edges that connect claims to supporting actions, artifacts, and checks. Through data-analysis and coding examples, we show how the resulting traces expose workflow decisions, artifact lineage, repair steps, validation coverage, and claim-support paths for evidence-centered audit.

## 二、论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想
- 以**证据为中心**重新组织智能体会话记录。LEDGER 不替代可观测性系统，而是建立在已捕获的观测记录之上，将其重构成分层语义追踪图。
- 核心设计原则：**追踪记录（Trace Records）** 与**图结构（推断层）** 明确分离，底层记录确定性保留、上层结构允许解释性推断，并保留可追溯性。

### 2.2 分层追踪图的三层结构

**第一层：Trace Records（追踪记录）**
- 最细粒度的原子记录，对会话中“发生了什么”进行确定性保存。
- 包含：消息内容、工具调用与结果、生命周期事件、工件引用、时间信息、原转录本链接。
- 通过 Codex 生命周期钩子（SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, Stop）捕获 JSON 载荷，并复制完整 transcript JSONL 作为事实来源。
- 构建 trace.json 摘要，将转录行归一到稳定记录族：会话/轮次上下文、可见消息、工具调用/结果、生命周期事件、推理摘要、解析错误、覆盖记录等。

**第二层：Evidence Nodes（证据节点）**
- 将紧密相关的 Trace Records 分组为可检查的工作单元，例如将工具调用请求与结果通过共享 group id 合并为一个节点。
- 类型分两类：
  - **Action 节点**（蓝色）：控制、用户消息、助手消息、工具调用四个类别（见表1）。
  - **Artifact 节点**（橙色）：可检查的对象，如文件、补丁、代码、表格、图表（表1中的 artifact 类别）。

**第三层：Workflow Nodes（工作流节点）**
- 将相关证据节点聚合为工作流阶段，便于以阶段粒度审查长会话。
- 六个类别（表2）：context（上下文）、plan（计划）、inspect（检查）、execute（执行）、validate（验证）、claim（声明/结论）。

### 2.3 Artifact 节点与语义边
- Artifact 节点从工具调用记录及其结果中恢复（文件路径从命令文本中解析），充当“证据锚点”，使声明能连接到可检查的具体对象。
- **七个带类型语义边**（表3）：frames（框架）、uses（使用）、produces（产生）、informs（告知）、checked_by（被检查）、supports（支持）等，均为有向边，遵循追踪顺序但仅在存在语义关系时添加。

### 2.4 LEDGER 侧车追踪器（Sidecar Tracer）
- 以旁路方式与实际会话并行运行，无需修改智能体本身。
- 捕获路径依赖 Codex 的 hook 配置 + transcript 重建，但论文强调该方法不限于 Codex——任何暴露类似钩子与转录记录的编码智能体都可构建同类型追踪图。

### 2.5 审计界面的三重视角
1. **图引导的工作流审查**：双层级图（Workflow + Evidence），先看阶段覆盖，再深入证据层。
2. **证据检查**：节点详情 + 工件视图（终端输出、补丁、文件、图表、表格等），图只是进入原始记录的索引。
3. **追踪构建审计**：事件与日志视图展示 Trace Records、图更新、模型调用记录、追踪错误等，让图构建过程本身可审计，可区分智能体错误与追踪系统错误。

### 2.6 信任边界
- Trace Records 由确定性解析产生，可独立信任；Evidence Nodes 和 Workflow Nodes 由追踪智能体（tracer agent）读记录后推断产生，属于解释层，存在不完整、不稳定或错误的可能。界面保留底层记录以便审查结构构建的可靠性。

## 六、论文的主要结论与发现

1. **数据案例分析——工件血缘（Artifact Lineage）路径成立**：
   - 追踪图清晰展现了从源文件 → 清洗步骤 → 生成的表格/图 → 最终报告的完整链条。
   - 审查者能从最终声明出发，沿 support 边反推到生成工件的脚本创建、失败执行、修复补丁、成功重跑和预览命令。
   - 系统暴露了显著的“错误—修复”序列（首次脚本执行因 Markdown 表格依赖缺失而失败，后续追踪到补丁与重跑），以及质量检查工件（缺失值表）与报告证据并列呈现。

2. **编码案例——代码定位（Code Grounding）路径成立**：
   - 追踪图区分了**智能体主动设计的实现**与**后续修复的部分**：首次实现通过测试后，又新增了缺失节点处理的 guard patch、回归测试补丁和第二轮测试。
   - 在最终 diff 中两阶段合并为一个函数，但追踪中它们是分离的阶段，使审查者能区分“设计行为”与“事后发现边界情况”。
   - 第一次测试覆盖有序访问行为，回归测试覆盖 guard，最终报告只称“一次通过运行”，而追踪图能告诉审查者**每个检查覆盖到什么行为**，而非仅知道检查存在。
   - 文件读取与检索记录（短路径导出搜索、泛型模块读取、邻近测试读取、文档列表检查）在 Workflow 层面被分开，设计选择（有序段组合、复用现有最短路函数）因此是可验证的。

3. **总体结论**：LEDGER 的分层追踪图范式能有效将“声明—证据”关系从需要用户手工重建变为可遍历路径。Trace Records 确定性保存事实，而证据/工作流节点和语义边使记录可被用作审查对象。

## 七、优点：方法与实验设计上的亮点

1. **证据记录与推断结构分离**：Trace Records 由确定性解析产生，独立的“追踪构建审计”视图让图构造可被检查，避免将解释混同为事实；用户可区分智能体错误与追踪系统错误。
2. **三层粒度设计合理**：Trace Records（原始）、Evidence Nodes（可检查工作单元）、Workflow Nodes（阶段级视图）层层递进，兼顾细节保留与全局可读性。
3. **工件作为证据锚点**：文件、补丁、表格、图表等作为独立 Artifact 节点连接图中，审查者能直接打开实物验证，而非仅依赖描述。
4. **声明到证据的可遍历路径**：typed semantic edges（支持/产生/检查等）使审查者可逆序遍历，从结论回溯到证据，符合人类“证据中心审查”的思维方式。
5. **不侵入智能体**：以 sidecar 方式运行，不修改被审智能体；捕获路径基于通用钩子与转录记录，架构可迁移至支持类似接口的其他智能体。
6. **案例互补性好**：数据分析（工件血缘）与编码（代码定位）两个案例覆盖了不同的关键审查维度（数据流 vs 代码变更流），演示了系统的一般适用性。
7. **坦诚讨论限制**：明确承认图构建层非完全确定性，并将其定位为“审计辅助”而非“事实来源”，方法论上严谨。

## 八、不足与局限

### 8.1 图构建的不确定性问题
- **核心限制**：Evidence Nodes 和 Workflow Nodes 由追踪智能体推断产生，可能不完整、不稳定或错误。例如哪个 Trace Record 归为哪个节点、选什么类型、语义边是否恰当，都依赖模型判断。
- 这与推理忠实性（Chain-of-Thought 不忠实）、可监测性和溯源的根本性挑战相关，论文承认未来应尽可能用确定性或独立可验证的结构（更强的插桩、结构化工具记录、数据溯源后端）替代模型推断。

### 8.2 实验覆盖不足
- 仅两个案例、无量化评估、无用户研究、无消融实验、无与基线（如 Graph of Trace、LangSmith 等）的对比。
- 数据流细节（如表格/列级依赖）目前需从命令文本和输出预览中恢复，恢复质量未经系统评估。
- 未测试长会话（数百/数千步骤）、多智能体协作、复杂分布式工具链等压力场景下的图可读性与构建性能。

### 8.3 方法局限
- 审计路径依赖会话中存在干净的文本可解析性（路径、命令），若工具不暴露结构化记录，捕获可能不完整。
- 边类型（uses/informs/supports/checked_by）在长会话中的边界可能模糊，未来需区分时间、数据流、验证、证据关系等更细粒度类型。
- 图可视化在大规模会话中可能产生视觉拥塞，论文承认需更好的视觉编码（区分确定/推断结构、突出无支持声明、按声明/工件中心显示子图）。

### 8.4 普适性与评估偏差风险

- 案例由论文作者自行设计并审查，存在“作者偏差”风险；提示词设计可能无形中影响智能体行为，使追踪图显得比实际更清晰。
