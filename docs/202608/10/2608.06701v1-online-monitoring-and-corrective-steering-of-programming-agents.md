## 摘要
修复大型项目中的GitHub问题是一项长周期任务，尤其当修复需要跨多个位置修改或问题描述缺乏定位和修复所需信息时。因此，代理会经历漫长且容易低效和出错的轨迹：偏离预期计划、重复失败操作，或在没有有效补丁的情况下终止。本文提出LivePlan，用于实时监控、检测和纠正此类行为低效和偏移。LivePlan将评判与建议解耦：一个基于规则的确定性监控器检查轨迹上的通用信号以检测问题，无需调用LLM；仅在检测到问题时，才咨询顾问LLM获取高层级的下一步纠正。这种设计避免了先前方法中误导性的重新规划和昂贵的干预。我们在SWE-agent之上实现LivePlan，并使用五个LLM（三个作为执行代理，两个作为顾问）在SWE-bench Verified和SWE-bench Pro上进行评估。与原始SWE-agent相比，LivePlan显著提高了问题解决率，实现了高达15.2%（平均9.9%）的持续增益，同时每个实例仅增加0.08美元的成本。额外的解决方案集中在中等和困难实例上。LivePlan在解决率上持续优于替代方法，在已成功运行上的回归极小，并在无基线解决的问题上取得新的成功。

## Abstract
Fixing GitHub issues in large-scale projects is a long-horizon task, especially when a fix requires changes across multiple locations or the issue description lacks the information needed to localize and repair it. As a result, agents traverse long trajectories that are prone to inefficiency and error: they drift away from their intended plan, repeat failed actions, or terminate without a working patch. This paper proposes LivePlan to monitor, detect, and correct such behavioral inefficiencies and drifts in real time. LivePlan decouples judging from advising: a deterministic, rule-based monitor examines general signals over the trajectory to detect issues without invoking an LLM, and only when an issue is detected does it consult an advisor LLM for a high-level, next-step correction. This design avoids the misleading re-planning and costly interventions of prior approaches. We implement LivePlan on top of SWE-agent and evaluate it using five LLMs (three as executor agents and two as advisors) across SWE-bench Verified and SWE-bench Pro. Compared to vanilla SWE-agent, LivePlan notably improves issue resolution rates, achieving consistent gains of up to 15.2% (average: 9.9%), while incurring only an additional cost of $0.08 per instance. The additional solutions concentrate on medium and hard instances. LivePlan consistently outperforms alternative approaches in resolution rate, with minimal regression on already successful runs and new successes on problems that no baseline solves.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究对象**：基于 LLM 的编程代理（programming agents）在大型代码库上修复真实 GitHub issue 的**长时程任务**（long-horizon task）。
- **核心痛点**：这类任务中，代理需要遵循一个预设的计划流程（定位→复现→打补丁→验证），但在执行过程中极易出现两类问题：
  - **行为漂移**：跳过关键阶段（如不验证就提交）、反复执行失败动作、陷入无效思考循环、长时间停滞在某一阶段等，导致轨迹低效甚至失败。
  - **信息不足**：当 issue 描述缺少定位和修复所需信息，或修复需要跨多个文件时，代理更容易"迷失方向"。
- **既有方法的三大缺陷**（论文归纳）：
  1. **评判与建议耦合**：一个 LLM 同时扮演"判断是否出错"和"给出修正建议"两个角色，而 LLM 有"取悦提示"（sycophancy）倾向，容易被激励去"找出问题"，从而产生**虚假问题**并给出误导性建议，干扰原本正常执行的轨迹。
  2. **触发时机不当**：要么在轨迹结束后进行事后分析与重跑（成本高、纠正太晚、新计划可能有害），要么周期性检查（频率过高则昂贵、过低则反馈滞后）。
  3. **LLM 作为评判者不可靠**：既会漏报真实问题，也会误报虚假问题，且非确定性高。

## 2. 论文提出的方法论

### 核心思想
**解耦评判与建议**：用一个**确定性的、基于规则的监控器（Monitor）**持续检测轨迹中的行为漂移，只有在检测到问题时才调用**LLM 顾问（Advisor）**生成高层级的下一步纠正建议。这样避免了 LLM 幻觉出不存在的问题，也避免了不必要的昂贵干预。

### 关键技术细节

**（1）监控器（Monitor）：基于两种过程中心轨迹表示**

- **GRAPHECTORY**：将轨迹转换为富图，节点是不同的代理动作（并新增"思考"节点），边是执行顺序。
- **LANGUTORY**：将底层动作抽象为问题求解阶段序列（导航、复现、修补、验证）。
- 监控器在每一步动作执行前，先"试探性"更新这两种表示，然后用确定性算法检测是否触发行漂移。

**（2）十种行为漂移信号（分阻塞型与非阻塞型）**

| 类型 | 信号 | 说明 |
|---|---|---|
| 阻塞型 | Plan Violation | 跳过计划阶段，如"过早修补"（未定位就修补）、"跳过修补"（未产出补丁就提交）、"跳过验证"（未验证就提交） |
| 阻塞型 | Thought Oscillation | 重复思维模式，无实质进展 |
| 阻塞型 | Action Oscillation | 重复执行循环，如自环或循环动作序列 |
| 非阻塞型 | Long Stagnation | 同一阶段停留过长（导航/复现/修补/验证中的某个阶段过久） |
| 非阻塞型 | Repeated Action | 重复执行相同动作，如反复查看已看过的位置 |

**（3）顾问（Advisor）**

- 检测到漂移后，优先使用**预定义建议**（如"长期停滞——导航"给出三条具体建议）。
- 若冷却时间（θc=5步）已过，则调用 LLM 顾问生成**定制建议**，输入包括：问题描述、自上次建议以来的轨迹切片、上次建议、预定义建议（作为提示）。
- 输出是**下一步建议**（而非长程新计划），避免过度约束执行器。
- 冷却机制避免频繁调用 LLM，控制成本和延迟。

**（4）干预处理器（Intervention Processor）**

- **阻塞型漂移**：拒绝执行当前动作（丢弃试探性状态更新），将建议附加到执行器历史中；最多连续干预 θi=5 次，避免卡死。
- **非阻塞型漂移**：允许执行当前动作，但附加建议以调节后续决策。

**（5）算法流程（简要）**
```
每步：
  1. 执行器提出下一步动作
  2. 监控器试探性更新轨迹表示，检测漂移规则
  3. 若无漂移 → 执行动作并提交
  4. 若有漂移：
     → 取预定义建议
     → 若冷却已过 → 调用 LLM 顾问获取定制建议
     → 若为阻塞型且未超最大次数 → 丢弃该动作，追加建议
     → 否则 → 执行动作并追加建议
```

## 6. 论文的主要结论与发现

1. **LivePlan 显著提升解决率**：在 SWE-bench Pro 上，相比 Vanilla 提升 +5.45 到 +15.24 个百分点；SWE-bench Verified 上提升 +5.00 到 +11.20 个百分点（平均 +9.9%）。
2. **成本极低**：每个实例仅增加约 $0.08 平均成本；监控器几乎是零开销；顾问成本仅 $0.01–$0.06/实例。对 MiniMax-M2.5 在 Verified 上甚至降低了总成本（$0.30→$0.23）。
3. **新增解决集中在中等和困难实例**：SWE-bench Pro 上几乎全部新增解决属于中/难类别。
4. **优于所有基线与消融**：比 SAGE 解决率更高且成本更低（SAGE 常因生成幻觉化的全局计划而失败，甚至低于 Vanilla）；比 Periodic Advisor（过度干预、误导性强）和 Predefined Advice（仅预定义建议不够充分）均更优。
5. **过程质量改善**：LivePlan 将阻塞性漂移大幅降低（如 Plan Violation 在 Pro 上从 55.63% 降至 34.37%，Verified 上从 40.27% 降至 13.67%）；计划遵从度评分（PPC/POC/PC）显著提高。
6. **干预确实改变了轨迹**：前缀 LCS 相似度（干预前）高（0.8–0.9），干预后显著下降，说明干预带来的修正不是执行随机性所致。
7. **LivePlan 的回归（R→U）极少**：根因不是建议错误或干预不及时，而是执行器无法忠实遵循正确建议。
8. **非确定性稳健性**：在 Vanilla 结果一致的确定性子集上，方法排名和增益大小均保持。

## 7. 优点

### 方法设计上的亮点

1. **解耦评判与建议**：解决了 LLM 同时当"裁判"和"教练"的角色冲突问题，消除了 sycophancy 偏差和幻觉性误报。
2. **确定性监控器**：基于规则（图的后边、环、阶段长度等），可复现、零成本、不幻觉，不受 LLM 非确定性影响。
3. **"仅在需要时干预"**：可比周期干预节省大量顾问调用（干预触发率从 ~99% 降至 83–94%）。
4. **建议粒度恰当**：输出"下一步建议"而非"全局新计划"，既给执行器有效引导又避免过度约束，防止上下文污染。
5. **双重建议机制**：预定义建议（稳定、零成本）+ 定制 LLM 建议（灵活、问题特定），兼顾可靠性与泛化性。
6. **阻塞/非阻塞分级**：对高风险漂移（跳过关键阶段）执行阻断，对低风险漂移（效率问题）仅附加建议，保持灵活性。
7. **冷却机制**：避免频繁调用 LLM，控制成本与延迟。
8. **增强的轨迹表示**：在图表示中加入 thought 节点，并拆分了导航/复现阶段，能捕捉更细粒度的行为问题。

### 实验评估上的亮点

1. **三层实验体系**：结果层（解决率/成本）、过程层（漂移检测率、计划遵从度、轨迹相似度）、机制层（U→R 与 R→U 的案例根因分析）。
2. **人工案例研究**：对改善和回归案例进行人工标注与根因归纳，深入揭示方法何时有效、为何失效。
3. **非确定性控制**：用确定性子集验证结论稳健性，并用统计检验确认干预效果的显著性。
4. **成本透明度高**：分别报告执行器、顾问、监控器各自的成本与延迟，表明增量成本来源于更长的成功轨迹而非更昂贵的干预。

## 8. 不足与局限

### 实验覆盖与偏差

- **执行器非确定性未完全控制**：论文在 RQ5 中仅对 Vanilla 的两次运行做一致性筛选，但 LivePlan 自身的运行只跑一次，未验证其自身结果的可重复性；非确定性分析只在一个模型上进行额外验证。
- **SAGE 运行方式可能有不利偏差**：虽然论文按原样运行 SAGE 的官方流程，但 SAGE 的失败被归因于其生成错误的全局计划（如定位不存在的文件），不排除 SAGE 在超参数或配置上未达到最优表现。
- **部分基线为近似实现**：SWE-PRM 和 Wink 无可运行工件，用 Periodic Advisor 作为近似类比；论文指出 Predefined Advice 是其对应技术的"上界"，这虽客观但仍非直接对比。
- **数据集 2 个且均为 SWE-bench 系列**：未在除 SWE-bench 系列之外的基准（如 RepoBench、其他多语言仓库）上验证。

### 方法本身的局限

- **需要更强的顾问 LLM**：论文明确表示顾问必须比执行器更强才有意义，这限制了对等模型场景的适用性。
- **执行器遵从度是关键瓶颈**：R→U 案例中大多数根因是执行器无法遵循正确建议，说明方法不能保证执行器忠实执行建议——这是未来"干预感知的后训练"需要解决的问题。
- **监控信号的不完整性**：论文承认信号是一般性的，可能不完整（依赖可配置信号库，用户可扩展），某些漂移类型（如"有害的但符合计划的行为"）可能漏检。
- **非阻塞性漂移的模糊性**：长期停滞既可能是低效，也可能是解决难题的合法需求，阈值 θp=7 的设定可能误判真实需要的探索。
- **预定义建议的通用性有限**：虽然提供了"下一步建议"的粗粒度引导，但对复杂问题可能不够具体。

### 成本与可扩展性

- **顾问延迟**：MiniMax-M3 的顾问平均延迟 29.1–39.5 秒，在需要实时干预的场景下仍可能构成瓶颈。
- **上下文切片设计的潜在信息损失**："自上次建议以来的轨迹切片"可能丢失更早期的关键上下文，尤其当问题需要跨长距离推理时。

### 其他注意点

- 论文的时间标注为 2026 年，部分引用（如 GPT-5.2-Codex、MiniMax-M3、SWE-bench Pro 等）相对于当前现实属于未来/假设性内容，需注意其真实可用性。
- 未讨论防御性场景（如对抗性提示注入到 issue 描述或代码中）对监控器的影响。
