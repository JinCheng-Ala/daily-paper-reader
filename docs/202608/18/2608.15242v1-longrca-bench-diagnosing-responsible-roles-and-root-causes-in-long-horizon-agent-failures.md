## 摘要
当长时程智能体执行失败时，结果级评估能揭示失败结果，但无法指出决定性的错误是在哪一步进入轨迹的。开发者因此必须检查完整执行过程，以识别责任角色并定位最早的决定性根因步骤。现有的失败归因基准主要聚焦于较短轨迹，对跨越数百个记录步骤的诊断研究不足。我们提出了LongRCA Bench，包含五个领域中的1,140条无注入错误的失败轨迹，并提供了独立评分的人员标注，标注了责任角色和最早决定性根因步骤。轨迹的中位步数为145步，最强基线仅达到13.2%的精确根因步骤准确率。我们进一步提出了根因轨迹归因（RCTA）方法，这是一种无需训练的方法，从分段摘要中检索候选错误步骤，并将其追溯到先前可用的交接指令。使用相同的骨干网络、基准实例和评分协议，RCTA在责任角色识别上达到51.1%的准确率，在精确根因步骤定位上达到24.1%的准确率。这些结果凸显了在长轨迹故障诊断中，需要将责任角色归因和精确根因步骤定位作为独立目标进行评估。

## Abstract
When a long-horizon agent execution fails, outcome-level evaluation reveals the unsuccessful result but not where the decisive error entered the trajectory. Developers must then inspect the full execution to identify the responsible role and localize the earliest decisive root-cause step. Existing failure-attribution benchmarks largely focus on shorter traces, leaving diagnosis across hundreds of recorded steps underexplored. We introduce LongRCA Bench, comprising 1,140 failed trajectories across five domains without injected errors. It provides independently scored human labels for the responsible role and earliest decisive root-cause step. The median trajectory contains 145 steps, and the strongest baseline reaches only 13.2% exact root-step accuracy. We further present Root-Cause Trajectory Attribution (RCTA), a training-free method that retrieves candidate error steps from segment summaries and traces them to available earlier handoff instructions. Using the same backbone, benchmark instances, and scoring protocol, RCTA reaches 51.1% responsible-role accuracy and 24.1% exact root-step accuracy. These results highlight the need to evaluate responsible-role attribution and exact root-step localization as separate targets in long-trajectory failure diagnosis.

## 1. 核心问题与研究动机

- **研究背景**：大语言模型（LLM）驱动的智能体越来越多地通过长序列的规划、工具调用、多角色协调、执行和验证来完成复杂任务。当这些执行失败时，**结果级评估（outcome-level evaluation）只能揭示最终的不成功结果，却无法指出决定性的错误是在哪一步进入执行轨迹的**，也无法判断哪个工作流角色应当为此负责。
- **核心痛点**：当数百个记录步骤将最初错误与最终失败分隔开来时，人工检查完整执行轨迹以定位根因变得极其困难且耗时。
- **定义两个独立任务**：
  - **根因定位（Root-cause localization）**：找出引入与最终失败相关的最早决定性错误的最早记录步骤。若某个错误在最终失败前已被成功修复，则不应被选为根因。
  - **责任角色归因（Responsible-role attribution）**：识别对失败负责的工作流角色。有效的角色标签必须与源轨迹中记录的角色名匹配，且该角色不一定是所选根因步骤的发出者——两个输出被独立预测和评分。
- **现有工作的不足**：已有失败归因基准（如 Who&When、TraceElephant 等）大多聚焦于较短轨迹（平均 7.5~50.9 步），对跨越数百步的长轨迹诊断研究尚属空白。


## 2. 方法论

### 2.1 核心思想
- **RCTA（Root-Cause Trajectory Attribution，根因轨迹归因）** 是一个**免训练（training-free）** 的诊断方法，核心设计原则是：**将广泛的轨迹搜索与基于原始日志文本的聚焦证据比较相分离**。先通过分段摘要快速缩小候选范围，再结合早期交接指令进行精确归因。

### 2.2 方法的三阶段流程

**阶段一：轨迹分段（Segmenting the Trajectory）**
- 将长轨迹划分为连续的分段（segment），保持原始步骤ID。
- 基于规则的边界设置：字符上限 32,000 字符、每段最多 80 个非重叠步骤；边界可对齐日志中的完成标记或交接转换。
- 每个分段包含最多 5 个前序步骤作为重叠上下文，以保留边界附近的信息。
- 此过程不使用语言模型，完全由规则实现。

**阶段二：候选错误步骤召回（Recalling Candidate Error Steps）**
- 对每个分段调用一次 LLM，生成摘要并提出候选错误步骤（带记录ID）。
- 第二次调用将相邻分段摘要合并为按子目标（subgoal）组织的轨迹大纲（outline）。
- 汇总并优先排序所有候选 ID，检索每个保留步骤的原始文本。大纲提供全局进度信息，原始步骤文本为最终归因提供证据。

**阶段三：候选追溯至交接指令（Tracing Candidates to Handoff Instructions）**
- 对于执行者或验证者角色 Y 产生的候选步骤，检索最近一条发给 Y 的前序交接指令（X -> Y）；其他候选则获取最近的早期交接指令作为计划上下文。
- 最终 LLM 调用将候选步骤的原始文本与检索到的交接指令进行对比，遵循以下决策规则：
  - **交接指令已含错误**：若后续步骤执行了早期交接指令中已包含的错误决策，则选择交接指令步骤为根因。
  - **交接后引入新错误**：若后续步骤偏离交接指令或引入了指令中不存在的新决定性错误，则后续步骤为根因。
  - **已修复错误**：在评估器确认失败前已被纠正的早期错误排除在外。
  - **验证器漏检**：验证器未能检测早期错误不取代引入错误的步骤。
- **独立输出**：最终输出负责任角色和根因步骤两个独立字段，根因选择不决定角色预测。

### 2.3 输出验证
- 程序化验证器检查：预测角色是否出现在轨迹中、根因和支持 ID 是否引用记录步骤、引用的交接文本是否真实存在于所指指令中。
- 无效响应获得一次带验证反馈的重试机会；仍无效则移除不支持字段并标记审查或弃权。


## 3. 实验设计

### 3.1 基准构建：LongRCA Bench
- **数据规模**：1,140 条失败轨迹，共 178,137 个记录步骤；平均长度 156.3 步，中位数 145 步，最大 728 步。
- **数据来源**：五个自然失败（无注入错误）的来源基准：
  - SWE-bench Pro（128 条，软件修复）
  - Terminal Bench 2（42 条，终端任务）
  - TravelPlanner（685 条，旅行规划）
  - VitaBench（108 条，面向服务的工具使用）
  - WebArena Verified（177 条，网页交互）
- **轨迹生成模型**：MiniMax-M2.5（681 条）、Kimi-K2.5（276 条）、Qwen3.5-Plus（183 条）。
- **人工标注**：22 名计算机科学硕士/博士生参与标注，每条轨迹标注责任角色、最早决定性根因步骤和基于轨迹的书面理由；每条完整标注通常需要 30~40 分钟；所有标注经过逐条核查和分歧审查。

### 3.2 基线方法（全部使用 DeepSeek-V4-Flash 作为推理骨干）
- **All-at-once**：将完整轨迹一次性呈现给模型，要求单次调用返回角色和步骤。
- **Step-by-step**：顺序扫描轨迹，判断决定性错误是否已发生。
- **Binary search**：递归二分轨迹以定位根因区域。
- **ECHO**：层次化上下文表示 + 共识投票。
- **FALAT**：依赖引导搜索，遍历决策、工具输出和消息。

### 3.3 评估指标
- **负责任角色准确率**：显式角色输出与参考角色比较（独立于根因步骤）。
- **根因精确准确率**：预测步骤须精确等于 0-based 参考步骤。
- **根因 ±5 准确率**：绝对误差不超过 5 步。
- **源加权有效输出根因 MAE**：按源分层加权计算有效数值预测的平均绝对误差。

## 6. 主要结论与发现

1. **长轨迹失败诊断整体仍极难**：最强方法在精确根因步骤定位上仅达 24.1% 准确率，表明精确根因定位远未饱和。
2. **责任角色归因显著比精确根因步骤定位更容易**：RCTA 角色准确率 51.1% vs. 根因精确准确率 24.1%，说明两者是不同难度的能力维度，应分别评估。
3. **RCTA 显著优于所有基线**：相比最强基线 ECHO，角色准确率提高 23.6 个百分点，根因精确准确率提高 10.9 个百分点，±5 准确率提高 12.7 个百分点，MAE 降低 11.8 步。
4. **依赖引导搜索本身不足以应对长轨迹**：FALAT 的精确根因准确率（2.8%）甚至低于一次性提示（7.6%），说明仅靠依赖结构搜索在超长轨迹中效果有限。
5. **长距离归因是常态而非例外**：49.0% 的轨迹中参考根因后有超过 50 步的后续记录，28.4% 超过 100 步，7.7% 超过 200 步。


## 7. 优点

- **填补空白**：首次系统性构建了针对超长轨迹（中位数 145 步）的失败归因基准，覆盖 5 个任务域、3 种生成模型、多种智能体组织架构。
- **自然失败而非注入错误**：1,140 条均为真实执行中产生的失败轨迹，生态效度更高。
- **双目标独立评估**：责任角色与根因步骤分开预测、分开评分，避免角色预测成功掩盖定位能力的不足。
- **人工标注质量保障**：22 名 CS 研究生标注，每条包含书面理由；全量逐条核查 + 分歧审查，1,140 条全部人工覆盖，与许多仅抽样审查的基准形成对比。
- **方法设计合理**：RCTA 将「广度搜索」与「深度证据比较」分离——段摘要支持大范围快速扫描，最终归因则使用原始日志文本，避免摘要引入的信息丢失。
- **可复现性强**：提供完整 prompt 模板、SHA-256 哈希、推理配置、伪代码和输出验证规则，所有 20 个运行快照的 prompt 哈希一致。
- **决策规则明确**：对交接指令含错、交接后新错、已修复错误、验证器漏检等边界情况给出了清晰可操作的定义。


## 8. 不足与局限

- **精确根因定位准确率绝对水平仍然有限**：RCTA 虽远超基线，但 24.1% 的精确准确率意味着约 3/4 的失败案例仍无法精确定位根因步骤，实用价值受约束。
- **缺少消融实验**：候选召回、候选→交接追溯、反向指令检查、验证模块各自的贡献未被量化；作为未来工作提出，当前结论无法确认方法各组件的重要性。
- **标注成本极高**：每条轨迹标注需 30~40 分钟，限制了基准的可扩展性；且根因标注虽经多人审查，但论文未报告标注者间一致率（如 Cohen's κ 等）。
- **仅评估离线事后诊断**：不涉及在线失败检测、早期预警或干预，不能与奖励早期检测的协议直接比较。
- **角色空间受限**：只允许选择轨迹中已记录的角色；外部主体（如环境）不属于合法输出。这简化了任务，但也回避了「外部系统导致失败」的诊断场景。
- **分层分析不能推断因果**：轨迹长度、根因位置与源域、工作流相互混淆；>400 步分箱仅含 42 条轨迹且源构成不同，>400 步箱 RCTA 准确率 31.0% 应谨慎解读。
- **单一推理骨干**：所有方法仅使用 DeepSeek-V4-Flash 评估，未验证更强推理模型能否显著提升结果；结论只能支持「匹配骨干下的相对比较」。
- **中间因果链不评分**：RCTA 生成的中级因果链只是未评分的解释，不衡量完整因果链重建能力；根因定位的「正确」不一定意味着因果推理过程正确。
