## 摘要
现有评估往往将智能体故障简化为系统层面的结果，掩盖了故障来源以及哪种干预措施能够改进智能体系统。这产生了一个修复分配问题：相同的可见故障可能根据其来源需要模型后训练、框架工程、环境重新设计或基准修复。由于智能体行为产生于模型、框架、用户、工具、记忆和环境之间的交互，结果层面的标签通常不足以支持改进。大多数故障分类法对此问题帮助甚微，因为它们针对特定基准且缺乏共享结构。我们提出了一种面向交互的分类法，将故障定位到其产生的交互中，并识别出责任组件。该分类法将41种故障模式组织起来，为每种模式分配两个组件之间的一条边以及一个指示修复归属的故障侧。这使得分类法具有可操作性：模型侧故障确定后训练的目标，框架侧故障指向脚手架和工具集成修复，而环境或评估器故障则揭示需要重新设计的评估条件。该模式适用于各种智能体架构，从编码助手到长周期个人助手和多智能体系统。我们通过来自公开基准、模型系统卡片、已发表报告和记录的智能体轨迹的实例来夯实该分类法，并使用独立推理智能体作为评判者评估其可复现性。在四个前沿模型中，最强的评判者对人工类别标签达到了Cohen's κ=0.76，这表明这些类别捕捉到了共享结构而非注释者特定的偏好。

## Abstract
Existing evaluations often reduce agent failures to system-level outcomes, obscuring where the fault originated and which intervention would improve the agent system. This creates a repair-assignment problem: the same visible failure may call for model post-training, harness engineering, environment redesign, or benchmark repair depending on its source. Because agent behavior emerges from interactions among models, harnesses, users, tools, memory, and environments, outcome-level labels are often insufficient for improvement. Most failure taxonomies do little to resolve this problem because they are benchmark-specific and lack a shared structure. We introduce an interaction-centric taxonomy that localizes failures to the interactions in which they originate and identifies the responsible component. It organizes 41 failure modes by assigning each to an edge between two components and a fault side indicating where the repair belongs. This makes the taxonomy actionable: model-side failures identify targets for post-training, harness-side failures point to scaffolding and tool-integration fixes, and environment or grader failures reveal evaluation conditions requiring redesign. The schema applies across agent architectures, from coding assistants to long-horizon personal assistants and multi-agent systems. We ground the taxonomy in worked examples from public benchmarks, model system cards, published reports, and logged agent trajectories, and evaluate its reproducibility using independent reasoning agents as judges. Across four frontier models, the strongest judge reaches Cohen's $κ=0.76$ against human category labels, suggesting that the categories capture shared structure rather than annotator-specific preferences.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：现有智能体（Agent）评估体系存在"修复分配问题"（repair-assignment problem）——当智能体在复杂的长周期任务中失败时，研究者往往只看到一个系统级的结果（如"任务未完成"），却无法判断故障究竟源自哪里，因此也无法决定应该采取哪种修复手段：是模型的**后训练**（post-training）？是**框架工程**（harness engineering，即脚手架/工具集成）？还是**环境与评估条件重新设计**？
- **动机**：智能体行为是由模型、框架（harness）、用户、工具、记忆和环境等多个组件**交互涌现**出来的。同一个可见故障可能对应完全不同的根因。例如：智能体忽略早期用户指令，可能是由于框架的上下文压缩（context compaction）将该指令删除了（框架侧问题），也可能指令仍在但模型没有遵循（模型侧问题）。两者表面行为相同，但修复方向截然相反。仅靠"失败/成功"级别的结果标签，无法为系统迭代提供有效反馈。
- **现有工作的不足**：已有故障分类法或绑定于特定基准（SWE-bench、WebArena等），或仅针对多智能体协调等特定场景，或只是扁平列表，均**未指明责任组件**，因而无法将故障映射到具体干预措施。
- **本文主张**：故障定位必须区分"故障在哪个交互中显现"与"哪个组件导致了故障"。因此提出一种**面向交互的分类法**（interaction-centric taxonomy），将每个故障分配到两个组件之间的交互边（edge）上，并标注**故障侧**（fault side），从而把模糊的结果标签转化为明确的修复信号。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 组件词汇表

- 论文将智能体系统分解为12个组件，分为三个族（见下表与图1的径向交互图）：
  - **User族**：Owner（所有者，下达任务并定义成功标准）、Grader（评估者，通常对智能体不可见）、Third party（第三方，执行中遇到的非所有者代理/人）。
  - **Harness族**：Context（当前上下文）、Memory（持久记忆）、Tool（工具接口）、Model peer/subagent（其他模型，按角色区分为对等体或子代理，均通过各自框架交互）。
  - **Environment族**：Local env.（本地执行环境，如OS、文件系统）、External env.（外部服务，如API、网站、数据库）。
- 关键边界澄清：Grader与Owner分离（模型可能遵循了Owner却未满足Grader）；Third party与外部环境分离（前者是行为者，后者是传输通道；系统故障归环境，操纵行为归第三方）。

### 2.2 核心表示法

- 每个故障表示为：`COMP1 — COMP2 · fault: SIDE`（边+故障侧）。
- 示例：`TOOL — MODEL · fault: TOOL` = 工具包装器抑制了错误导致模型未观察到失败；`TOOL — MODEL · fault: MODEL` = 工具返回了错误但模型忽略了。
- 多智能体场景下，另一端也是模型，表示为 `MODEL — MODEL (role: PEER/SUBAGENT)`，peer/subagent 是角色而非组件。

### 2.3 根因归属规则

- 采用"最早不可恢复故障"（critical failure）原则：从观察到的系统级失败出发，沿因果链**向前追溯**（实际是回溯），标记导致执行无法恢复的最早事件，而非下游症状。
- 理由：对该点的干预原本会改变结局；后续错误可能只是它的后果。此规则防止注释者以不一致的方式为同一轨迹打标签。

### 2.4 分类法结构（41种故障模式）

- 按族和交互边组织，其中**36种归因于模型侧，仅5种归因于周围组件**（Context Rationale Erosion归框架，Instruction–Grader Mismatch归Owner，Mistranslation归Tool，Service Failure与Stale State Delivery归外部环境）。
- 单侧偏斜的原因在于归属规则：**"若一个更有能力的模型在相同条件下本可避免或恢复该故障，则归因于模型"**。
- 主要故障模式示例：
  - **User族**：Over-initiative（过度主动）、Under-initiative（主动性不足）、Satisficing（敷衍达标）、Instruction-Following Failure、Reasoning Failure、Unauthorized Irreversible Action（未经授权的不可逆操作）、Sycophancy（谄媚）、Domain Knowledge Deficit、Value Misalignment、Instruction–Grader Mismatch、Specification Gaming（规范博弈，攻击评估通道）、Evaluation Awareness（识破评估）、Indirect Prompt Injection（间接提示注入）、Contextual Sycophancy。
  - **Harness族**：State Tracking Failure（状态跟踪失败）、Goal Drift（目标漂移）、Context Rationale Erosion（上下文理由侵蚀，归因框架侧）、Memory系列（Missed Write、State Staleness、Overgeneralization、Memory Rationale Erosion、Pollution、Redundancy、Missed Read、Memory Following Failure）、Tool系列（Malformed Arguments、Suboptimal Arguments、Incorrect Tool Selection、Tool Hallucination、Tool Feedback Neglect、Tool Recovery Failure、Mistranslation）、多智能体系列（Delegation Failure、Communication Failure）。
  - **Environment族**：Service Failure（环境侧）、Stale State Delivery（环境侧）、Recovery Failure（模型侧）、Observation Failure（模型侧）。

### 2.5 安全影响标注

- 对具有安全影响的例子，额外标注OWASP Top 10类别（如Excessive Agency、Unbounded Consumption、Rogue Agents、Agent Goal Hijack、Misinformation、Sensitive Information Disclosure），每个例子最多一个最显著类别。

## 6. 论文的主要结论与发现

1. **分类法是有效的**：41个故障模式可以一致地映射到交互边+故障侧，使"哪里坏了、该修哪里"变得显式。最强的自动评判者（GPT-5.5）与人类标注的类别一致性达到κ=0.76，支持分类法的可复现性。
2. **故障定位确实影响干预方向**：同样可见的失败可能分别需要模型后训练、框架修改或环境/基准修复。例如E4（上下文压缩丢失"不要行动"指令后批量删除200封邮件）被标注为模型侧的Unauthorized Irreversible Action，而非框架侧的上下文压缩——因为"即使指令在，删除数百封邮件也是模型应当默认拒绝的高风险操作"；而E18/E21（压缩导致理由丢失而模型事后"反悔"）则归因于框架侧。
3. **责任分布高度偏向模型**：36/41的模式归因于模型。作者明确承认这是归属规则造成的偏向（"更强的模型本可避免"），并指出周围组件的5种模式是模型改进本身无法解决的硬边界。
4. **自动评判者的主要错误模式**是"当任务失败时，倾向于指责模型，即使真正故障在别处"（见附录A.2案例：评价环境的脚本回复邮件未送达，被评判者误判为模型没有主动检查收件箱）。这与OpenRCA 2.0报告的"无根据诊断"（ungrounded diagnosis）现象一致。
5. **根因追溯比模式选择更困难**：评判者在"给定黄金类别下选模式"时准确率更高（表3），说明类别错误会传导为模式错误；错误根源包括源材料证据不足、多模式症状重叠、因果链重建失败。

- **严谨的验证设计**：Agent-as-a-Judge流程模拟独立分析师（证据重建→分类→反思），且通过pre-tool hook阻断标注泄漏；使用三种指标（Acc、F1、κ）多维评估；选择性投票展示了实际部署时的精度–覆盖率权衡。
- **实证基础扎实**：40个实例均附有详细、可追溯的来源（GitHub issue、系统卡、轨迹日志），附录C给出了完整逐字定义与每个实例的机制分析，透明度高。
- **实践导向明确**：分类法直接指向干预——模型侧→后训练、框架侧→脚手架/工具修复、环境/评估器侧→基准/环境重设计；OWASP安全性标注进一步接了安全场景的地气。

## 8. 不足与局限

- **描述性而非定量性**：分类法不估计各故障模式的相对频率（作者明确指出不应将实例集用于频率推断）。40个实例是"具有说明性的精选集"，非随机样本，存在选择偏差。
- **证据依赖性强**：部分源材料（如E4的新闻报道）未提供完整轨迹，无法唯一确定根因；分类标签的质量受制于现有证据的详细程度。
- **单一人类标注者**：论文未呈现多位人类标注者之间的一致性指标（只有评判者–人类和评判者–评判者之间的κ），无法完全排除注释者个人偏见的残余影响，且"更强模型可避免"的归属规则本质上带有主观性。
- **自动评判准确率有限**：故障模式级的最佳κ仅为0.71，且评判者之间存在分歧（最低κ=0.61）；生产环境部署时可能需要选择性投票，而投票会降低覆盖率（68%），这意味着"最不确定的案例往往被弃权"，未能完全解决不确定性最大的诊断需求。
- **分类法动态性不足**：组件和模式随智能体架构发展可能需要扩充，作者也承认这一点；例如附录A.2中"脚本回复邮件未送达"这类纯框架bug被映射到最接近的EXTERNAL ENVIRONMENT边（Stale State Delivery），而非拥有专属模式——显示了分类法在真正混合/边界场景下的拟合度问题。
- **实验规模有限**：40个实例、4个模型、无消融（如移除反思步骤的效果、不同提示敏感度分析），且未评估评判者对同一实例多次判断的内部一致性（stability）。
- **计算资源与可复现性细节不足**：未披露推理算力规格、API成本、运行时长等，增加了复现难度。
