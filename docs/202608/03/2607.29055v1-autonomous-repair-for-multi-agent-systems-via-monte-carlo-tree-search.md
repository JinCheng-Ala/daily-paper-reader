## 摘要
多智能体系统（MAS）越来越多地被部署来解决复杂任务。当输出不正确或不令人满意时，用户必须通过检查智能体轨迹来手动定位智能体错误（即失败归因），并提供反馈以改进输出（即修复）。尽管最近在MAS失败归因方面有一些工作，但从这类错误中自动恢复的机制仍然在很大程度上未被探索。为了弥补这一差距，我们提出了MARS，一个基于搜索的框架，将MAS修复表述为蒙特卡洛树搜索（MCTS）过程，并通过诊断引导的扩展和基于分类法的评估来导航巨大的潜在修复空间。与标准MCTS通过完整 rollout 评估完整模拟不同，MARS使用部分 rollout 评估智能体轨迹以减少令牌消耗。此外，我们引入了StateMAS，一个大规模MAS修复基准，包含1,310条可重放的多智能体失败轨迹，涵盖四种类型的智能体架构和四种LLM骨干。在StateMAS上的实验表明，MARS在所有设置中始终优于最先进的方法，绝对改进从3.0%到12.1%，同时保持相当的令牌消耗成本。消融研究进一步证实，基于分类法的评估和诊断引导的扩展是实现这些性能提升的关键。

## Abstract
Multi-agent systems (MAS) are increasingly deployed to solve complex tasks. In case of incorrect or unsatisfactory outputs, users have to manually locate agent mistakes by inspecting agent trajectories (i.e., {\em failure attribution}) and provide feedback to refine the outputs (i.e., {\em repair}). Despite some recent work in MAS failure attribution, automated mechanisms to recover from such mistakes remain largely unexplored. To bridge this gap, we propose MARS, a search-based framework that formulates MAS repair as a Monte Carlo Tree Search (MCTS) process and navigates the vast space of potential repairs via diagnosis-guided expansion with taxonomy-augmented evaluation. Unlike standard MCTS, which evaluates a complete simulation via full rollout, MARS evaluates the agent trajectory using partial rollout to reduce token consumption. Furthermore, we introduce StateMAS, a large-scale MAS repair benchmark with 1,310 replayable multi-agent failure trajectories spanning four types of agent architectures and four LLM backbones. Experiments on StateMAS demonstrate that MARS consistently outperforms state-of-the-art methods, achieving an absolute improvement from 3.0\% to 12.1\% across all settings, while maintaining a comparable token consumption cost. The ablation study further confirms that taxonomy-augmented evaluation and diagnosis-guided expansion are critical to achieving these performance gains.

## 2. 方法论

### 2.1 核心思想

MARS 将 MAS 修复定义为一个搜索问题：给定初始失败轨迹 τ_fail，搜索一系列修复干预 δ = (t, ϕ)（回滚步骤 + 修复操作），使系统最终产出正确输出。它通过 MCTS 在巨大的干预空间中系统性地探索替代修复方案，而非像 DoVer 那样提交单一路径的完整轨迹再生成。

### 2.2 关键技术创新

**（1）部分 Rollout（Partial Rollout）与专用动作空间**

标准 MCTS 通过完整 rollout 评估节点，但对 MAS 而言完整执行代价极高。MARS 设计了三个专用动作：

- **Rollback（回滚）**：截断到故障步骤 t，删除后续轨迹，保留有效前缀，恢复系统状态以便修复；
- **Guided Repair（引导修复）**：注入修复指导 ϕ 到下一轮智能体提示中，从回滚点恢复执行至多 L 步；
- **Continuation（延续）**：不加修复指导，从当前状态继续执行 L 步，扩展有潜力的部分轨迹。

**（2）诊断引导的节点扩展（Diagnosis-guided Expansion）**

LLM 动作选择器先检视节点上存储的诊断反馈 f，确认失败归因是否准确（避免 LLM 评委误判）；确认后依据失败原因决定回滚步骤并生成具体修复建议 ϕ；若判断无误则倾向于延续轨迹。分支因子上限为 K。

**（3）分类法增强的评估机制（Taxonomy-Augmented Evaluation）**

由于部分 rollout 无最终结果可评估，MARS 引入：
- **MAST 分类法的 14 种失败模式**（如步骤重复、违反任务规格、忽略其他智能体输入、过早终止等）作为检查清单，指导 LLM 评委识别部分轨迹中的早期失败迹象，输出诊断反馈 f；
- **五级评分规约（r ∈ [0,1]）**：Verified Completion (1.0)、Strong Progress (0.8–0.9)、Moderate Progress (0.5–0.7)、Limited Progress (0.2–0.4)、Failure/Divergence (0.0–0.1)，并强调对"工具证据支持"和"独立答案重推导"的强制要求，以抑制幻觉。

**（4）算法流程（文字版）**

1. **选择（Selection）**：从根节点起按 UCT 公式（Q(c)/N(c) + C·√(ln N(p)/N(c))）选择未完全扩展的节点；
2. **扩展（Expansion）**：LLM 动作选择器根据诊断反馈执行 rollback / guided repair / continuation，应用动作创建子节点并执行 L 轮；
3. **评估（Evaluation）**：LLM 评委对子节点轨迹打分 r 并给出诊断反馈 f，存储于节点；
4. **回传（Backpropagation）**：标准 MCTS 沿搜索路径更新 N 和 Q 值。评分 r=1 时提前终止，最终返回得分最高的轨迹。

## 3. 实验设计

### 3.1 基准：StateMAS

- **构成**：1,310 条可重放的 MAS 失败轨迹，涵盖 **4 种智能体架构**（centralized / sequential / decentralized / concurrent）× **4 种 LLM 骨干**（Qwen3.5-9B、Qwen3-30B-A3B、Nemotron-3-Nano-30B-A3B、GPT-5.4-mini）；
- **任务来源**：GAIA（66 个免费任务为 GAIA-Free 分区，99 个付费任务为 GAIA-Comm 分区）和 AssistantBench（33 个验证任务）的完整验证集；
- **数据特性**：每个执行步骤记录可重放的系统状态快照（上下文、智能体记忆、运行时变量、工作区文件），LLM 温度设为零以保证确定性重放；提供 API 支持从任意步骤恢复和修改执行。
- **智能体团队**：采用 Magentic-One 的五智能体团队，跨架构保持一致以隔离通信结构的影响。

### 3.2 对比方法

- **DoVer**：现有唯一 MAS 自动修复方法（仅限 centralized 架构）；
- **Reflexion 基线**：对失败轨迹生成反思并以线性方式插入反馈后继续执行；
- **ReAct 基线**：通过顺序推理-行动循环逐次干预和重执行（与 MARS 共享动作空间但无树搜索）。

### 3.3 评估指标

- **初始通过率（Initial pass rate）**：MAS 修复前正确解决任务的比例；
- **修复后通过率（Post-repair pass rate）**：对初始失败的轨迹应用修复后成功解决的比例。

## 6. 主要结论与发现

1. **MARS 在所有设置下均优于现有方法**：与最强基线相比，在 centralized 架构下 GAIA 提升 7.8%–9.7%，AssistantBench 提升 6.1%–9.1%；跨全部 4 种架构绝对提升 3.0%–12.1%。
2. **性能提升不以 token 开销膨胀为代价**：MARS 的 token 消耗与最经济的基线（ReAct）相当（仅高 14.0%–38.7%），相对性能提升（56.2%–92.5%）远超 token 相对开销；相比 Reflexion，token 减少 1.6%–54.7%。
3. **消融实验确认关键设计有效**：移除分类法评估后通过率从 30.3% 降至 25.8%；线性搜索（K=1）降为 22.7%；全 rollout 虽同等通过率但 token 消耗暴涨至 3.14M（vs. 861K）。
4. **结果具有一定稳定性**：3 次重复的最小-最大差异不超过 3.0%。

## 7. 优点

1. **填补研究空白**：首次将 MCTS 系统性地应用于 MAS 自动修复，超越 DoVer 的线性搜索和中央协调器限制，扩展修复到任意轨迹点、任意架构。
2. **工程创新性强**：部分 rollout 与专用动作空间（Rollback / Guided Repair / Continuation）的配合，在显著节省 token 的同时保持搜索精度；Rollback 在再次回滚时避免了不必要的重执行。
3. **评估机制务实**：分类法增强评估将 MAST 的失败模式与五级评分规约结合，并通过"工具证据引用 + 独立答案重推导"强制约束，有效抑制 LLM 评委的幻觉，从机制层面提高了中间节点评估的可靠性。
4. **基准贡献大**：StateMAS 是目前最大规模的 MAS 修复基准，覆盖 4 架构 × 4 骨干 × 1,310 条可重放失败轨迹，且提供确定性重放接口，为后续研究提供了可复用的公共评测平台。
5. **实验设计相对严谨**：包含 token 成本分析、消融、随机性和敏感性分析，评估维度较全面。

## 8. 不足与局限

1. **框架依赖**：StateMAS 基于 Microsoft Agentic Framework 构建，检查点与重放机制对其他 MAS 框架（如 LangGraph）的迁移可能需要适配，通用性受限。
2. **任务域覆盖有限**：任务仅来自 GAIA 和 AssistantBench，集中于通用助手和网页导航场景，未覆盖代码生成、机器人控制、对话管理等其他 MAS 典型应用域，领域泛化性未验证。
3. **评估覆盖不完整**：GAIA-Comm 和 AssistantBench 分区仅用 centralized 架构，16 种配置未全量跑完所有任务，存在偏置风险；消融实验也仅覆盖单一模型/架构/分区。
4. **LLM 评委可靠性**：评估依赖 LLM-as-a-Judge，虽然设计了验证机制，但评委本身的误差（误判、幻觉、对部分轨迹的误读）无法完全消除，且未报告与人工评估的一致性验证。
5. **成本披露不足**：未明确报告 GPU 硬件、总 API 费用和运行时长，影响复现和成本估算。
6. **无 oracle 假设下的局限**：搜索终止条件依赖 LLM 评委的"Verified Completion"判断，若评委给出错误的 r=1，将提前终止并返回错误轨迹；作者未分析这种错误接受（false acceptance）的发生率。
7. **统计功效有限**：随机性分析仅重复 3 次，且敏感性分析未进行显著性检验，难以严格判断观察到的差异是否显著。
