## 摘要
现有对微服务自动化根因分析（RCA）的评估主要依据端点正确性来评判诊断性能：即方法是否定位到负责的服务。这一标准便于比较，但无法揭示诊断的证据基础或连接故障源与观察到的症状之间的故障传播路径，而值班站点可靠性工程师需要这两者来判断是否应采取行动。因此，我们将RCA视为一个可观测的诊断过程。我们的轨迹级框架根据人工整理的、服务级别的故障传播路径来评估智能体执行过程。应用于一个公开的微服务RCA基准测试，它分析了3,500条诊断轨迹，刻画了智能体在何处进行调查以及如何使用检索到的遥测数据。我们发现答案正确性与诊断质量之间存在脱节：智能体可能定位到故障源，却未能重构其传播过程。成功的调查会保持在故障影响表面上，基于检索到的证据采取行动，并随着搜索加深而扩展其查询手段。失败则源于关键证据被遗漏、检索到的证据被误解，或用无根据的推断替代缺失的证据。我们将这一分类体系实现为DiagGuard，一种两阶段纵深防御架构，其中grounding阶段在定位前审查可用观测，verification阶段则对照观测审计诊断结果。在一个使用不同模型、基准测试和服务拓扑的独立设置中，DiagGuard将Acc@1从43.5%提升至52.5%。这些结果表明，轨迹级评估能暴露被最终答案指标所掩盖的局限性，并为改进自动化RCA提供可操作的指导。

## Abstract
Existing evaluations of automated root cause analysis (RCA) for microservices assess diagnostic performance mainly by endpoint correctness: whether a method localizes the responsible service. This criterion enables comparison but does not reveal the evidentiary basis of a diagnosis or the fault-propagation route connecting the source to observed symptoms, both of which an on-call site reliability engineer needs to judge whether action is warranted. We therefore treat RCA as an observable diagnostic process. Our trajectory-level framework evaluates agent executions against manually curated service-level fault-propagation paths. Applied to a public microservice RCA benchmark, it analyzes 3,500 diagnostic trajectories, characterizing where agents investigate and how they use retrieved telemetry. We find a disconnect between answer correctness and diagnostic quality: an agent may localize the fault source yet fail to reconstruct its propagation. Successful investigations stay on the fault-impact surface, act on retrieved evidence, and broaden their query repertoire as the search deepens. Failures arise when decisive evidence is omitted, retrieved evidence is misinterpreted, or unsupported inference substitutes for missing evidence. We operationalize this taxonomy as DiagGuard, a two-stage defense-in-depth architecture in which grounding surveys available observations before localization and verification audits the diagnosis against them. In an independent setting with a different model, benchmark, and service topology, DiagGuard raises Acc@1 from 43.5% to 52.5%. These results show that trajectory-level evaluation exposes limitations hidden by final-answer metrics and provides actionable guidance for improving automated RCA.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究动机**：现有微服务根因分析（Root Cause Analysis, RCA）的自动化评估几乎只关注"最终答案"——即是否正确定位到根因服务（Acc@k、MRR、MAP 等终点指标）。但值班 SRE 不仅需要一个根因标签，还需要判断该诊断**是否有充分证据支撑**、故障是否沿着合理的传播路径影响了症状服务。
- **核心问题**：仅仅评估最终定位正确性会掩盖诊断过程的缺陷。同一正确标签可能建立在强证据或弱证据之上；错误诊断如果只看标签，则无法揭示其推理在哪里失败，也无法沉淀为可复用的改进经验。
- **整体含义**：作者主张将 RCA 视为**可观测的诊断过程**，提出"轨迹级（trajectory-level）"评估框架，以人工校验的服务级故障传播路径为过程级基准，分析 LLM 智能体在诊断过程中如何查询遥测、形成假设、使用证据并最终给出结论，从而揭示终点指标无法暴露的能力边界和系统性失败模式，并将这些失败模式转化为可落地的防御机制。

## 2. 方法论

- **核心思想**：把 RCA 从"定位任务"重构为"轨迹级诊断过程评估"——用**人工标注的服务级故障传播图 G\* = (V\*, E\*)** 作为过程级 ground truth，对智能体的每一步思考、动作和返回结果进行标准化，并与该传播图对照分析。
- **故障传播路径标注**：对 RCABench 的每个案例，基于故障注入元数据、注入前后 trace/metrics/logs，以及 TrainTicket 服务调用图，人工重建从根因服务到 SLO 告警服务的传播路径，作为 Node F1 与 Edge F1 的基准。
- **轨迹归一化**：将异构智能体的运行过程归一化为三元组序列 T = [τ₁, …, τₙ]，每个 τᵢ = (thought, action, result)；对可输出 SQL 的四个框架，将动作统一为对共享遥测存储的 SQL 查询，使跨框架可比。
- **指标定义**：
  - Acc@1：预测根因是否属于真实根因集合；
  - pass@k：多次运行中至少一次命中；
  - Node F1 / Edge F1：预测传播图与真实传播图在服务节点/有向边上的重合度；
  - causal-chain depth：根因到 SLO 服务的最短路径长度，作为诊断难度分层依据。
- **行为与意图分析**：为每轮轨迹标注 primary service、导航转移类型（Advance/Regress/Lateral/Return/Off-Path 共 10 种）、证据利用率（utilized/partial/ignored/no_data）；为每条 SQL 标注 11 种 SRE 诊断意图和 6 个确定性标签轴（granularity、window、time、emission、resource_family、symptom_signal）。
- **失败模式编码**：将错误轨迹对照"预期证据"编码为三类失败族：
  - OMIT（协议遗漏）：本可查询的决策性证据从未被检索；
  - MIS（语义误读）：证据被检索到但被错误解释；
  - GEN（一般推理缺陷）：无证据支撑的推断替代了缺失证据。
- **干预设计 DiagGuard**：由三类失败模式驱动的两阶段纵深防御：
  - **Grounder**（接地防御）：在定位前系统性盘点现有观测数据，强制对照正常窗口、检查未探索的指标维度；
  - **Verifier**（验证防御）：在给出最终诊断前进行自我审计和健全性检查，避免证据未收集或误读时草率提交结论。

## 6. 主要结论与发现

- **RQ1：效果与成本**
  - 开放式、自适应的通用智能体（ThinkDepth.ai 79.2%、AIQ 77.6%、Claude Code 79.6%）显著优于强约束的编排式方法（TaskWeaver 65.2%、OpenRCA 46.6%、MABC 42.6%），但同一模型下 top 框架差距仅 2.0 pp，而换用更强 backbone（Sonnet, 90.0%）带来 10.8 pp 提升——**backbone 模型是主导杠杆**。
  - 准确率随因果链深度增加而下降，Sonnet 在深层案例上几乎不衰减。
  - **Edge F1 普遍远低于 Node F1**：识别受影响的异常服务比恢复有向传播边容易；即使定位正确，✓ Edge F1 最高仅 0.67。
  - 失败运行反而消耗更多轮次（额外 7–11.4 轮），说明高预算来自无效搜索而非证据积累。
- **RQ2：行为与意图**
  - 成功诊断**保持在故障影响表面上**并基于检索证据行动（utilized 比例高）；失败诊断更频繁 Stray/Wander/Retrace，且 ignore 证据或遇到空查询。
  - Sonnet 在 54.3% 的轮次中利用前一轮结果，Qwen 仅 24.9%。
  - Sonnet 的意图更丰富：中段转向 metric_enum、callgraph、resource_probe、network_flow；Qwen 则陷在 trace_follow 和 log/keyword_search 的浅层循环中，导致在需要深层资源证据的故障类型（Resource 75% vs. 94%、JVM 66% vs. 93%）上差距最大。
- **RQ3：失败分类学**
  - 错误诊断收敛为三类证据处理失败：**从未收集决策性证据（OMIT）**、**收集但误读（MIS）**、**无根据推理覆盖证据（GEN）**。
  - Qwen 主要败于遗漏（基线缺失、资源未探测等），Sonnet 主要败于语义误读（如噪音即病因、语义误读、schema 外臆造）。
- **RQ4/RQ5：DiagGuard 干预**
  - 在 held-out 设置（Seed 2.0 Pro / AIOps 2025）下，Acc@1 从 43.5% 提升至 52.5%（+9.0），pass@3 +10.2，pass@5 +10.7；9 类故障全部有增益（DNS +1.0 到 I/O +20.8）。
  - 消融显示 Grounder 单独贡献 +4.5，Verifier 单独贡献 +4.1，全量 +9.0——两者互补、近乎可加。

## 7. 优点

- **问题视角新颖**：从"答案是否正确"转向"诊断过程是否合理"，首次以人工标注的故障传播路径作为轨迹级 ground truth 来评估 RCA 智能体。
- **框架系统完整**：从路径标注、轨迹归一化、指标设计、行为/意图编码到失败模式挖掘，形成了完整的"测量—分析—干预"闭环。
- **大规模实证**：3,500 条轨迹、92,501 条 SQL 动作、154 条失败轨迹人工编码，规模在同类研究中较大。
- **人工标注质量控制**：传播路径双重标注一致性 93%、意图标签人类一致性 κ=0.83、失败模式编码一致性 93.5%，并公开数据与代码以支持复现。
- **结论可操作**：不仅描述失败，更将失败分类学落地为 DiagGuard 架构，并在完全独立的模型/基准/拓扑上验证，增强说服力。
- **发现具有实际价值**：指出 edge 重建比 node 识别更难、backbone 模型比框架架构更能影响效果、失败运行消耗更多 token——这些结论对 RCA 系统设计与预算控制有直接参考意义。

## 8. 不足与局限

- **外部效度受限**：主研究仅基于 RCABench（TrainTicket）单一拓扑与单一采样集；虽然 DiagGuard 在 AIOps 2025 上做了跨验证，但 RQ1–RQ3 的行为规律是否适用于其他拓扑/栈/部署仍不确定。
- **统计效力不足**：RQ1–RQ3 中每种配置只运行一次，未报告标准差或显著性检验；不同框架间的实现差异和 prompt 差异可能引入混杂，未必能完全归因于"框架架构"本身。
- **过程分析覆盖不全**：MABC 与 OpenRCA 因无可比 SQL 轨迹被排除在行为/意图分析之外，导致"过程级结论"只覆盖四个通用框架。
- **LLM 辅助标注偏差**：意图分类与失败模式编码依赖 LLM 分类器和人工审查，尽管多重校验，仍可能存在 judge 偏差和主观性。
- **成本与实践门槛**：顶级通用智能体每案例约 $0.2（Qwen）或 $4.6（Sonnet），Sonnet 成本是 Qwen 的 20 余倍；DiagGuard 在 AIOps 2025 上每案例成本达到 $0.16，若大规模部署仍需考虑经济性。
- **干预验证的边界**：DiagGuard 的验证仅在一个 held-out 设置上完成，未在更多模型中测试其稳定性和通用性；其对真实生产环境中复杂、长时间、多根因故障的适用性尚待检验。
