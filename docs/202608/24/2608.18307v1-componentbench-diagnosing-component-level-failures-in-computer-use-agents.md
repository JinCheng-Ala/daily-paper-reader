## 摘要
当前对计算机使用代理的评估分为长时程工作流基准测试和原子级GUI接地测试。这留下了一个缺乏工具支持的中间层：真实的组件中心交互（例如，切换一组按钮），这些交互足够简短以便诊断，又足够丰富以捕捉现代界面的负担。我们提出了ComponentBench，一个针对现代Web UI上计算机使用代理的组件级评估的基准测试和诊断流程。ComponentBench围绕一个与库无关的97个规范UI组件本体组织，这些组件在广泛使用的组件库中实例化为2,910个程序化验证的任务，并与干净的人类参考轨迹配对，从而能够评估任务成功率和交互效率。除了任务收集之外，我们引入了一个可扩展的流程，用于在实现后审计实际的结构难度，并跨任务和组件族综合结构化失败分析。评估七个模型——GPT-5.4、Gemini 3 Flash、GPT-5.4 mini、GPT-5 mini、Gemini 3.1 Flash-Lite、Qwen3-VL-235B和UI-TARS-1.5-7B——跨四个观察和动作空间，我们表明这些设计选择对性能有重大影响。在单个共享测试平台内，仅改变观察和动作空间就会使同一模型的任务成功率变动超过30%：GPT-5 mini从使用可访问性树观察的83.1%下降到仅使用坐标像素控制的48.9%。此外，即使最快的配置所花时间也是匹配的人类参考的3.7倍，而且对人类来说微不足道的空间操作仍然对当前代理构成挑战。

## Abstract
Current evaluation of computer-use agents is split between long-horizon workflow benchmarks and atomic GUI-grounding tests. This leaves an under-instrumented middle layer: realistic component-centered interactions (e.g., toggle a button set) that are short enough to diagnose and rich enough to capture the burdens of modern interfaces. We present ComponentBench, a benchmark and diagnostic pipeline for component-level evaluation of computer-use agents on modern web UIs. ComponentBench is organized around a library-agnostic ontology of 97 canonical UI components instantiated as 2,910 programmatically verified tasks across widely used component libraries, paired with cleaned human reference trajectories that enable evaluation of both task success and interaction efficiency. Beyond task collection, we introduce a scalable pipeline for auditing realized structural difficulty after implementation and synthesizing structured failure analyses across tasks and component families. Evaluating seven models -- GPT-5.4, Gemini 3 Flash, GPT-5.4 mini, GPT-5 mini, Gemini 3.1 Flash-Lite, Qwen3-VL-235B, and UI-TARS-1.5-7B -- across four observation and action spaces, we show that these design choices critically impact performance. Within a single shared harness, changing only the observation and action space shifts task success by more than 30% for the same model: GPT-5 mini falls from 83.1% with accessibility-tree observations to 48.9% with coordinate-only Pixel control. Moreover, even the fastest configuration takes 3.7x as long as the matched human reference, and spatial manipulations that are trivial for humans continue to challenge current agents.

# ComponentBench：诊断计算机使用代理的组件级故障——论文总结

## 一、核心问题与整体含义
- **研究动机**：现有计算机使用代理（computer-use agents）的评估体系存在**两极分化**：一端是长时程工作流基准（如 WebArena、VisualWebArena、OSWorld 等），能测端到端能力但难以定位失败根因；另一端是原子级 GUI 接地测试（如 ScreenSpot、ScreenSpot-Pro），只测"能否找到元素"却忽略了现代组件常需的短多步交互。
- **缺失的中间层**：真实的、以组件为中心的交互（如设置日期、拖动滑条、在多选框中提交筛选）——既短到可诊断，又丰富到能体现现代界面的真实负担。
- **核心含义**：长任务可靠性受限于组件级交互可靠性；若一次工作流包含多个关键组件交互，单个组件 80% 的可靠性会使端到端成功率骤降。因此需要专门针对组件级失败的系统性诊断工具。

## 二、论文提出的方法论
- **核心思想**：构建一个**库无关的组件本体**，将每个任务锚定到单一"主组件"上，并配备程序化验证器、人类参考轨迹和结构化难度审计，从而同时评估"能否完成"和"完成得是否高效/直接"。
- **组件本体**：结合 WAI-ARIA APG 与主流 React 组件库（Ant Design、MUI、Mantine 等），归纳出 **97 种规范组件类型**，归入 **14 个交互族**（如日期时间、拖放、高级编辑器等），并定义 **24 种任务模板**。
- **任务生成与实现**：
  - GPT-5.2 Pro 按 YAML 架构生成任务规格；
  - Claude Code 将规格实现为真实的 Next.js 页面（非静态 mock）；
  - 人类操作员对每个任务执行两次并录制低层动作轨迹，清洗后保留较短者作为参考。
- **程序化验证**：每个任务有独立 JS 验证器，检查**提交后的最终状态**而非中间草稿状态；要求显式提交（Apply/Save/Confirm）的任务只验证提交后状态；同时枚举负例避免近似状态误判。验证器状态与代理观察隔离（如成功 banner 不会泄露信息，所有 `data-testid` 属性被剥离）。
- **四种观察/动作空间**：
  - **AX-tree**：截图 + 可访问性树文本，通过元素 ID 操作；
  - **Set-of-Marks (SoM)**：截图叠加编号框，通过元素 ID 操作；
  - **Pixel**：仅截图，通过坐标操作；
  - **Browser-Use**：外部工具丰富框架（含 DOM 序列化和 grounded elements），一个模型回合可执行最多 4 个原始动作，作为工具丰富的参考模式。
- **难度审计**：区分"意图难度"（设计时标注）与"实现难度"（通过 Playwright 重放人类轨迹，提取 24 维结构特征，如目标尺寸、间距、叠加深度、选项密度等，聚合成 7 个难度轴）。
- **诊断管道**：三层结构——Layer 1 组装任务数据包，Layer 2 生成任务级观察，Layer 3 聚合为组件级报告。基于全量证据进一步蒸馏出 **ComponentBench-Core**（912 个硬任务、45 个组件、19 个生成单元），集中压测未解决的交互模式。

## 三、实验设计
- **基准规模**：
  - ComponentBench-Full：2,910 个程序化验证任务，覆盖 97 个组件类型、14 个交互族，主要使用 Ant Design / MUI / Mantine，另有 30 个外部 markdown 编辑器任务；
  - ComponentBench-Core：912 个重新生成的硬任务，用于压力测试。
- **评测模型**：7 个模型——Gemini 3 Flash、GPT-5.4、GPT-5.4 mini、GPT-5 mini、Gemini 3.1 Flash-Lite、Qwen3-VL-235B、UI-TARS-1.5-7B（其使用原生 pixel-only harness）；另对 Opus 4.6 在 Core Pixel 上单独评测。
- **对比方式**：主要不是与其他基准赛跑，而是在同一任务集上对比**不同观察/动作空间**（AX-tree、SoM、Pixel、Browser-Use）和模型能力层级，以及 vs 人类参考轨迹。
- **评价指标**：20 步预算内的任务通过率；效率指标（≤H/≤2H/≤3H/≤5H，H 为人类参考步数）；平均耗时与耗时比；场景因子（杂乱度、间距等）的影响；失败轨迹分类。
- **额外验证**：重复运行稳定性（278 任务子集 × 2 次）、多标注者人类参考验证（278 任务 × 3 人）、对抗性失败案例审查（20 个案例，由独立模型 reviewer 复核）。

## 四、资源与算力
- 论文明确：模型 API 访问由 **Amazon AGI SF Lab** 提供，实验运行在 **Duke CS cluster** 上。
- 部分实现细节提及：Qwen3-VL-235B 使用本地 vLLM FP8 服务（AX/SoM/Pixel 模式），UI-TARS-1.5-7B 使用单 GPU bfloat16；Opus 4.6 通过 Anthropic computer-use 工具接口。

## 五、实验数量与充分性
- **实验量大**：7 个模型 × 4 种模式（UI-TARS 仅原生模式）在 2,910 个任务上运行；加上 Core 上额外模型；失败轨迹分析约 8,864 条（5 个模型），Layer-2 LLM 诊断 2,752 次运行。
- **充分性较好**：
  - 提供了 bootstrap 95% 置信区间（half-width ≤ 1.9%）；
  - 做了重复运行稳定性检查（最大偏差 1.4%）；
  - 有人类标注者间一致性验证（步数比 1.05× 远小于人-代理差距）；
  - 场景因子（杂乱、间距、主题、实例数等）有系统抽样与控制。
- **存在的不足**：
  - 主结果多为**单次运行**（除 278 任务子集外），任务级结果存在波动；
  - Browser-Use 的"步"定义不同于其他模式（最多 4 个动作/步），效率比较存在乐观偏差；
  - 模型 API 端点、精度（如 Qwen Browser-Use 经 Bedrock）不完全一致，可能引入微小偏差；
  - 虽未发现任务质量问题，但对 LLM 生成规格可能带来的正则性没有彻底审计污染风险。

## 六、主要结论与发现
1. **观察/动作空间的选择极大影响性能**：同一模型仅改变观察/动作空间成功率可变动超过 30%（GPT-5 mini：AX-tree 83.1% → Pixel 48.9%）；且 Set-of-Marks 的效益是模型依赖的：对较弱模型显著提升（GPT-5 mini +29.6%），对 GPT-5.4 / GPT-5.4 mini 反而略有负作用。
2. **效率是部署瓶颈**：即使最快配置（GPT-5.4 mini SoM）也要 3.7× 人类时间；GPT-5 mini Pixel 平均每个成功任务要 71.8 秒（21.5× 人类时间）。
3. **空间操作组件对人类简单但对代理困难**：滑条、拖放列表、分割器等 9 类组件人类仅需 ≤2 步但代理平均通过率 <60%；如 resizable columns 仅 24.4%，window splitter 38.3%，slider range 39.9%。
4. **视觉上下文对纯 pixel 模式惩罚更重**：中等杂乱使 Pixel 下降 14.3% 而 AX-tree 仅下降 0.2%；紧凑间距使 Pixel 下降 13.6%，AX-tree 下降 4.5%。部分模型的最佳观察空间会因杂乱度而反转。
5. **失败机制可分类**：连续校准错误（20.2%）、瞬态状态丢失（19.9%）、缺失提交/确认（11.6%）、目标获取/错误实例（11.2%）、重复无进展循环（11.2%）、组件特定流程缺失（9.6%）等；无进展循环通常是深层机制问题的症状而非根因。
6. **ComponentBench-Core 仍具挑战性**：相比 Full，各模型通过率下降 10–39%；Opus 4.6 在 Core Pixel 上为 65.4%，仍留下超 1/3 任务未解决。

## 七、优点
- **填补评估空白**：定位于长时工作流与原子接地之间，提供真实且可诊断的组件级中间层。
- **大规模且程序化验证**：2,910 个任务全部由确定性验证器打分，避免 LLM 主观评判；验证器与观察隔离，防作弊设计严密。
- **人类参考轨迹**：同时评估任务成功率和效率，且人工轨迹经过清洗和多标注者验证。
- **跨库、可控场景因子**：同一组件在多个库中实现，支持跨库泛化分析；8 个场景因素（主题、间距、布局、杂乱等）受控变化。
- **结构化诊断管道**：从任务包到组件级报告，配合失败分类法和对抗性案例审查，使基准不止于排行榜，而能定位具体失败机制。
- **区分意图难度与实际难度**：重放人类轨迹提取真实结构特征，避免实现改变难度导致的误判。
- **Core 蒸馏**：将饱和的易任务剔除，集中质量于未解决部分，作为紧凑的压力测试工具。

## 八、不足与局限
- **范围限制**：仅覆盖 Web（Next.js/Chromium），不含桌面与移动界面；未涵盖所有野外的定制组件（如 CAPTCHA 类任务被排除）。
- **评估目标有限**：只测组件级能力，不测长程规划；组件级表现如何预测端到端工作流成功率未做验证。
- **人类参考的非最优性**：主要参考轨迹来自单一标注者两次通过（虽然附加验证显示标注者间差异小），且树/DOM 工具代理可能有人类不可见的更短非视觉路径。
- **运行随机性**：主表结果单次运行；重复运行显示任务级结果对边界任务存在翻转，尽管聚合指标稳定。
- **生成偏差风险**：规格由 GPT-5.2 Pro 生成、页面由 Claude Code 实现，可能存在生成器特有规律；污染未被彻底审计。
- **接口差异**：GPT 模型未用官方 Operator/Computer Use API，Opus 4.6 未用完整 Anthropic 环境，BrowserGym 不渲染可见光标，可能低估原生接口表现。
- **结果时效性**：模型版本更新迅速，本文结果只是特定时间快照。
