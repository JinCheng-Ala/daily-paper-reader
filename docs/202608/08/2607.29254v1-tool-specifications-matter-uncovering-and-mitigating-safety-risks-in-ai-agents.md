## 摘要
AI代理通过外部工具扩展大型语言模型（LLM），使其能够执行复杂任务并将模型输出转化为实际世界中的重大行动。然而，LLM在作为代理部署时往往变得不太安全，而这种性能下降的来源仍未被充分理解。在本文中，我们确定了模式化格式的工具规格是代理安全性下降的主要来源，并通过白盒表示分析表明，它们削弱了模型内部的拒绝信号，并导致不安全的工具执行。基于这一发现，我们提出了SafeKeep，一种推理时的安全防护措施，将安全判断与工具执行解耦：它使用扁平化的文本工具规格来评估请求，同时保留原始模式化格式的规格用于执行。在两个代表性基准测试和四个LLM（包括白盒和黑盒模型）中，SafeKeep将有害请求的平均拒绝率从23.8%提高到70.6%，并将观察级提示注入下的平均攻击成功率从25.6%降低到2.5%。它还优于现有的安全防护措施，并保持了任务处理能力。我们在https://github.com/snowcatsmoking/SafeKeep 发布代码和数据。

## Abstract
AI agents extend large language models (LLMs) with external tools, enabling them to perform complex tasks and translate model outputs into consequential real-world actions. Yet LLMs often become substantially less safe when deployed as agents, and the source of this degradation remains poorly understood. In this paper, we identify schema-formatted tool specifications as a primary source of agent safety degradation and show, through white-box representation analysis, that they weaken the model's internal refusal signals and contribute to unsafe tool execution. Building on this finding, we propose SafeKeep, an inference-time safeguard that decouples safety judgment from tool execution: it assesses requests using flattened textual tool specifications while retaining the original schema-formatted specifications for execution. Across two representative benchmarks and four LLMs, including both white-box and black-box models, SafeKeep increases the average refusal rate for harmful requests from 23.8% to 70.6% and reduces the average attack success rate under observation-level prompt injection from 25.6% to 2.5%. It also outperforms existing safeguards and preserves task-handling capability. We release the code and data at https://github.com/snowcatsmoking/SafeKeep .

## 2. 方法论

### 核心思想

SafeKeep 的核心是将**安全判断与工具执行解耦**：安全判断阶段使用**扁平化的文本形式**工具规格（避免 schema 格式对模型内部表示的干扰），执行阶段保留**原始 schema 格式**工具规格（不改变 Agent 原有工具调用接口）。其设计动机来源于机制层面的发现：schema 格式的工具规格会诱导模型隐藏状态沿一个与拒绝方向相对（opposing）的方向移动，从而削弱拒绝信号。

### 关键技术细节

**（1）来源定位分析（§3）**

- 使用 **拒绝方向（refusal direction）** 作为诊断工具：拒绝方向通过有害/良性请求在特定层激活均值之差提取，输入在该方向上的投影作为拒绝分数，AUROC 衡量有害-良性可分性。
- 将 Agent 上下文分解为三个组件：**角色描述（role description）**、**工具使用指令（tool-use instructions）**、**工具规格（tool specifications）**，逐步添加组件观察 AUROC 变化。
- 使用**长度匹配对照（Chatbot-Long）** 排除"长上下文本身导致退化"的替代解释。
- 分别操控工具规格的**语义内容**与**表示形式**：将 schema 格式转为扁平文本（改变表示、保留语义）；将词法内容替换为伪词（改变语义、保留表示结构）。

**（2）机制分析（§4）**

- 定义 **Schema Direction**（公式 2）为同一工具规格在 schema 格式与文本格式下的隐藏状态差异均值，分有害/良性两个类别分别计算。
- 分析各层 Schema Direction 与聊天机器人拒绝方向（chatbot-derived refusal direction）的余弦相似度，发现有害请求的 Schema Direction 在所有层都与拒绝方向呈负对齐。
- 分析首个生成 token 在拒绝方向上的投影，验证 schema 格式在解码阶段削弱有害-良性分离。
- **激活引导（activation steering）**（公式 3）：在峰值拒绝层，从隐藏状态中减去单位化的有害请求 Schema Direction（强度 α 控制），提供因果关系证据——α=4 时拒绝率从 5% 提升至 47.5%，有害执行率从 95% 降至 45%。

**（3）SafeKeep 框架（§5）**

- **安全判断阶段**：构建包含安全评估者角色、原始 Agent 角色与指令、扁平化文本工具规格、用户请求的评估上下文，模型输出 YES（不安全）/NO（安全）。该阶段使用同一底层 LLM，无需微调或访问内部激活。
- **执行控制阶段**：NO 则转发至原始 Agent 管线；YES 则阻止工具调用，预填充短拒绝前缀（如 "I'm sorry, but I can't help with that."），让模型自回归生成针对性拒绝。

### 适用性

SafeKeep 是模型无关的推理时方法，不要求参数更新或激活访问，可同时应用于开源白盒模型与商业黑盒模型。

## 6. 主要结论与发现

1. **schema 格式工具规格是安全退化的主导因素**：增量组件分析显示，添加工具规格后 AUROC 平均下降 0.136（最优层），远大于其他组件；长度匹配对照排除了长度效应。
2. **退化主要由表示形式而非语义内容驱动**：将 schema 格式转换为扁平文本后 AUROC 大幅回升（Llama：0.740→0.885）；而语义随机化保留 schema 格式时几乎无改善。
3. **机制层面**：schema 格式诱导的隐藏状态变化方向（Schema Direction）与拒绝方向在所有层呈负对齐（有害请求）；在首个生成 token 上，schema 格式显著压缩有害-良性请求在拒绝方向上的分离度。
4. **因果关系**：通过激活引导反向抵消 Schema Direction，模型行为从有害执行转向拒绝，验证了该表示变化对不安全行为有因果贡献。
5. **SafeKeep 有效性**：在四个模型上，AgentHarm 有害请求拒绝率从 23.8%（Base）提升至 70.6%，InjecAgent 平均攻击成功率从 25.6% 降至 2.5%；同时任务处理能力保持（AgentHarm Acc 从 60.9% 提升至 79.6%，InjecAgent Valid 显著提升）。
6. **扁平化文本表示是关键**：与 SafeJudge 对比表明，保留 schema 格式的自判断对安全提升有限，扁平文本表示是 SafeKeep 有效性的核心。

## 7. 优点

- **深入机制分析**：不仅提出防御方法，还利用拒绝方向、Schema Direction、余弦相似度、激活引导等多种白盒手段从描述到因果逐层解析安全退化的机制，方法严谨、证据链完整。
- **方法实用性强**：SafeKeep 无需训练、无需参数或激活访问，与底层模型和 Agent 框架解耦，可轻松集成到现有 Agent 管线（包括商业黑盒模型），工程部署成本低。
- **安全与能力兼顾**：不仅报告安全指标，还报告准确率和有效输出率，表明安全提升并非简单的"一律拒绝"式保守策略，而是精准区分有害/良性请求后的针对性拒绝。
- **控制实验设计出色**：长度匹配对照、语义/表示解耦、SafeJudge 消融等设计有效排除了多种混淆变量，结论可信度高。
- **消融对比有说服力**：SafeJudge（保留 schema 格式）与 SafeKeep（扁平化）的对比，直接证明了方法设计中对机制发现的转化是关键所在。

## 8. 不足与局限

- **算力与成本信息缺失**：未报告 GPU 型号、数量、运行时长等信息，难以评估方法部署的硬件要求。
- **实验基准规模有限**：仅两个安全基准，未评估更多元的安全风险场景（如多轮交互、记忆中毒、跨工具链路攻击等），在更广泛 Agent 场景下的适用性需进一步验证。
- **工具规格类型单一**：实验使用的工具规格均来自特定基准，其格式、复杂度和数量可能与真实生产环境有差异；极端复杂的工具集上的效果未知。
- **依赖自判断的可靠性**：SafeKeep 的安全判断仍依赖同样的 LLM，该 LLM 若被注入攻击或越狱诱导，自判断阶段的可靠性可能受损，论文对此未做专门分析。
- **黑盒模型上的安全提升幅度有限**：GPT5.4-mini 上 SafeKeep 的拒绝率提升（38.6%→57.4%）明显弱于 Llama（5.0%→72.2%）和 Gemini（40.3%→79.5%）的提升幅度，黑盒模型上的稳定性可能有待评估。
- **激活引导实验的规模较小**：表 3 的因果验证仅在一个模型（Llama3.1-8B-Instruct）和一套参数设定下完成，α 的敏感性分析未报告。
- **过度拒绝风险**：SafeKeep 在部分模型上 Acc 提升幅度大，但未详细分析对良性请求的误拒率，真实的良性任务误阻断率可能需要更多量化。
