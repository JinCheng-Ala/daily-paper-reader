## 摘要
代理技能为使用工具的语言模型代理封装了可重用的指令和资产。渐进式加载会产生故障边界，而基于会话、模型或工具的追踪难以描述这些边界：一项技能可能被发现但未被激活，被激活但没有指令，或者看似成功但缺少独立验证的结果。我们提出了技能运行时智能（Skill Runtime Intelligence），一种被动式运行时智能系统，可在异构环境中重构受支持的技能生命周期阶段，同时将不支持的阶段保留为未知。其运行全景（Run Panorama）将不可变事件、确定性关系、推断诊断和受控结果按四个证据等级进行区分；可选追踪导入和OTLP/HTTP导出支持现有可观测性部署。在六个冻结仓库配置文件、三个编码代理和七种干净或故障注入条件下，全部126次执行均保留了源代码工作树，且每次执行都精确关联到一个源代码会话。然而，适配器展现出三种不同的语义：无技能运行；完整运行但没有类似失败的事件；或在每次操作失败和干净会话中都出现类似失败的事件。在一项七模板诊断研究中，语义别名和全景图定位到相同的六个非干净边界，但在确切状态行为上有所不同；两种原始视图在所有18个干净案例上都发出失败状态，而全景图则不发出任何失败状态。一个已知规则图符合126/126个冻结契约，而第二个模型仅完成了228/378次调用。这些观察结果推动了可执行适配器资格认证，并表明事件存在不等于边界保真度，复合精确分数掩盖了不同的错误，模型解释不得覆盖确定性事实。

## Abstract
Agent Skills package reusable instructions and assets for tool-using language-model agents. Progressive loading creates failure boundaries poorly represented by session-, model-, or tool-centric traces: a Skill can be discovered but not activated, activated without instructions, or appear successful without an independently verified outcome. We present Skill Runtime Intelligence, a passive runtime-intelligence system that reconstructs supported Skill-lifecycle stages across heterogeneous harnesses while preserving unsupported stages as unknown. Its Run Panorama separates immutable events, deterministic relations, inferred diagnoses, and controlled outcomes with four evidence grades; optional trace import and OTLP/HTTP export support existing observability deployments.   Across six frozen repository profiles, three coding agents, and seven clean or fault-injected conditions, all 126 executions preserve source worktrees and each correlates to exactly one source session. Yet adapters expose three distinct semantics: no Skill runs; complete runs but no failure-like events; or failure-like events in every operational-failure and clean session. In a seven-template diagnostic study, semantic aliases and Panorama localize the same six non-clean boundaries but differ in exact/status behavior; both Raw views emit a failure status on all 18 clean cases, while Panorama emits none. A known-rule graph conforms to 126/126 frozen contracts, whereas a second model completes only 228/378 calls. These observations motivate executable adapter qualification and show that event presence is not boundary fidelity, composite exact scores mask distinct errors, and model explanations must not overwrite deterministic facts.

## 1. 核心问题与整体含义（研究动机与背景）

**背景**：语言模型代理（Agent）越来越多地通过"Agent Skills"获取可复用能力——即包含声明式元数据及可选脚本、引用和资源的目录。其规范采用 **渐进式披露（progressive disclosure）** 机制：轻量元数据可能在完整指令或资源加载之前即可见。这种设计提升了模块性，却带来了新的运维难题：**技能是否真正按预期运行了？**

**核心问题**：现有追踪手段存在三类典型的"失败边界"：
- **发现但未激活**（discovered but not activated）
- **激活但没有指令**（activated without instructions）
- **表面成功但无独立验证**（appear successful without independent verification）

**关键缺陷**：
- 仅凭代理的最终回答不足以作为证据——一个看似合理的回答后可能隐藏着激活失败、引用缺失、命令执行失败或产物未经验证等问题。
- 传统代理评估（如 SWE-bench）只衡量任务成功率或轨迹质量；通用追踪标准（如 OpenTelemetry）建模代理/工具 span，但**未将动态加载的 Skill 实例及其资源边界、证据等级作为首要实体**。
- 现有的会话、模型调用或工具追踪无法充分表征渐进式加载产生的失败边界。

**论文主张**：运维缺口并非"更多追踪"那么简单，而是**在不虚构观察的前提下，从异构、不完整的 harness 证据中重建可移植的 Skill 生命周期**。

## 2. 方法论

### 2.1 核心思想

提出 **Skill Runtime Intelligence（技能运行时智能）** ——一个**被动的运行时证据架构**，用于 Agent Skills。它观察现有代理工作流，而非代理模型请求或编排代理本身。关键设计原则是区分"事件存在"与"边界保真度"，并确保**模型解释不能覆盖确定性事实**。

### 2.2 Skill 生命周期模型

论文将一个 Skill 执行尝试表示为有序的 8 阶段生命周期：

> **Request → Discovery → Activation → Instructions → Resources → Execution → Artifacts → Outcome**

这些是逻辑边界，不要求每个 harness 对每个阶段都发射 span。例如，资源访问可直接被观察到，但该资源属于哪个 Skill 实例只能被确定性推导。这种分离避免了两种常见错误：将遥测缺失当作失败；将代理断言当作独立验证的结果。

### 2.3 系统架构（四层数据通路）

1. **Collectors（收集器）**：摄取官方钩子（hooks）、本地转录、只读文件系统或进程信号。
2. **Versioned adapters（版本化适配器）**：保留原始源记录，输出带时间戳和源溯源信息的通用事件信封。绑定 agent、agent 版本、adapter 版本和源格式。
3. **Evidence engine（证据引擎）**：构建会话（sessions）、轮次（turns）、Skill 运行、资源、工具、产物、结果及类型化关系。
4. **Panorama 与诊断器**：暴露生命周期、首个可观测分歧点、支撑证据和不可观测边界。

### 2.4 四种证据等级（Evidence Grades）

| 等级 | 含义 |
|---|---|
| **Observed** | 直接存在于源记录或外部验证器中 |
| **Derived** | 对观察记录进行确定性变换或关系推导 |
| **Inferred** | 不确定的模型或启发式解释；绝不静默提升 |
| **Experimental** | 来自声明受控实验的估计值 |

证据等级关涉"如何知道该主张"；因果范围是**独立的授权决策**——即使观察到子进程失败，也不能建立"Skill 导致结果"的因果效应。

### 2.5 确定性诊断图（Deterministic Diagnosis Graph）

证据引擎将每个生命周期阶段映射为：观察成功、观察失败、预期但未观察、不支持、或不适用。处理流程：

1. 追加不可变原始记录 → 2. 查阅 adapter 版本能力声明 → 3. 仅发出受支持的归一化字段 → 4. 按优先级附加确定性边 → 5. 遍历 8 个生命周期阶段 → 6. 仅在观察到失败或可评估的期望信号时发出 finding。

**边构造的固定优先级**：源父/子 ID → 显式 Skill 归属 → 活动 Skill 范围 → 精确产物路径 → 时间相邻性 → 模型/启发式建议。前四级可创建 Derived 边；后两级保持不确定，不能替代高优先级边。冲突的同优先级关系保留为**歧义**。

**模型限制**：模型分析接收最小化视图，返回结构化候选、状态、证据 ID 和因果标志，存储为 **Inferred**。生产契约不允许其覆盖图事实。

### 2.6 六项设计要求（R1–R6）

- **R1 观察但不接管**：不代理模型请求、不拥有代理循环、默认不阻塞操作。
- **R2 源保留**：原始记录不可变且独立可寻址；归一化不抹除源身份。
- **R3 知识论分离**：直接事实、确定性变换、不确定分析、受控效应估计不得共享一个无差别的置信度字段。
- **R4 版本化能力**：适配器是测量仪器，其 schema 和覆盖范围随 agent 版本变化；不支持的字段保持未知。
- **R5 隐私最小化**：提示、代码、路径、凭据、原始载荷对大多数生命周期诊断非必需。
- **R6 因果约束**：单次运行不能确立"技能导致结果"；此类声明必须来自受控重复试验并标记为 Experimental。

## 3. 实验设计

### 3.1 实验原则

- 在机器可读 manifest 中预注册条件矩阵和 gate。
- 源执行、遥测重建、代理响应、模型诊断是**分离的端点**。
- 失败的 gate 和格式错误的输出**保留在报告中**，不静默重试。
- 仓库通过冻结 Git 对象读取；SHA-256 绑定 fixtures、探针和报告。
- 类似 SWE-bench 的"可执行仓库基准"思路，但测量对象是 **Skill 生命周期证据**而非补丁正确性。

### 3.2 基准矩阵

**仓库配置**（6 个，每个包含 3 个冻结文件）：

| 配置 | 类型 |
|---|---|
| profile-01 | Go cache（模块配置、实现、测试） |
| profile-02 | Go telemetry（README、模块配置、agent） |
| profile-03 | Python research（打包、配置、激活） |
| profile-04 | Python app（README、依赖、应用） |
| profile-05 | Spec workflow（规范、辅助脚本、检查） |
| profile-06 | Skill catalog（README、Skill 定义、辅助脚本） |

**编码代理**（3 个）：

| Agent | 版本 | 模型/模式 | 环境 |
|---|---|---|---|
| Codex | 0.145.0 | gpt-5.6-sol | macOS arm64 |
| OpenCode | 1.18.5 | deepseek-v4-flash-free | macOS arm64 |
| Qoder | 1.1.10 | performance | macOS arm64 |

**条件**（7 种）：clean、instruction failure、missing resource、execution failure、artifact corruption、unverified outcome、verifier conflict。

**总体规模**：6 × 3 × 7 = **126 个执行单元格**（每格一次执行）。

**两个 gate**：
- **完整性 gate（integrity gate）**：每个单元格必须启动、保持工作负载、并精确关联到一个收集到的源会话。
- **响应 gate（response gate，更严格）**：代理必须返回精确的 nonce 绑定 oracle JSON。

**结构细分**（每个 agent 的 42 个会话）：24 个操作失败格 + 6 个干净格 + 12 个结果证据格（unverified outcome + verifier conflict）。

### 3.3 诊断效用研究

将 126 个案例变换为隐私安全 holdout（省略原始内容、路径、载荷、时间戳、源会话 ID）。**Gold 标签来自冻结故障 manifest 和确定性探针**，而非模型或人工裁决。

对比视图（5 种）：
1. **Raw model**：无序原生事件，最小结构；
2. **Semantics-matched Raw**：保留所有原生和辅助记录，内联别名暴露与 Panorama 等价的语义；
3. **Panorama model**：归一化生命周期阶段与证据等级；
4. **Known-rule graph**：确定性类型化关系候选；
5. **Graph+Model**：图候选 + 模型解释通道。

主模型条件下，每个案例在 Raw、Panorama、Graph+Model 三个视图中评估，即 **每后端 378 次调用**；语义匹配对照额外增加 126 次 Qwen 调用。

**主要指标**：精确边界与状态诊断、边界准确率、状态准确率、引用 ID 有效性、**引用蕴含性**（citation entailment，比 ID 存在更严格：被引记录必须支持预测关系）、因果安全性、完成率、延迟。

### 3.4 辅助压力测试

- **第一项**：19 条来自单一本地 Panorama 数据库的去标识化运行时追踪（每确定性发现画像最多 4 例），标签为生产规则候选（非人类 gold）。
- **第二项**：6 个预注册的规则外部图异常 + 6 个干净对照，测试受保护的假设生成。
- **盲化模型判定**：Qwen 和 Codex 仅看到 19 个去标识化证据图和冻结的分类 rubric，规则候选事后揭示。

### 充分性与客观性评估

**充分**：
- 覆盖 6 个不同仓库配置、3 种不同代理、7 种条件，跨多维度交叉形成矩阵。
- 双重 gate（完整性 + 响应）设计合理。
- 保留失败结果不重试，避免选择性偏差。

**局限**：
- **每格仅一次执行**——论文明确说明这建立的是"机制覆盖"而非"随机总体率"；无法估计代理行为的方差。
- 126 行实例化的是**7 个语义模板**，而非 126 个独立故障族——模板内行强依赖，因此**不报告案例级显著性检验**。
- 外部效度有限：单一本地数据库、单一远程主机、单一 PAI-DSW 实例。
- 已知规则图 126/126 符合是预期的契约一致性，**不是独立的诊断准确性**。
