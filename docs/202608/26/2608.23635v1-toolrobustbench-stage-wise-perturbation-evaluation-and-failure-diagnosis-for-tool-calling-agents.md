## 摘要
大型语言模型（LLM）依赖工具调用作为基本代理能力，使其能够调用外部系统并完成超出文本生成的任务。然而，纯粹的端到端（E2E）成功无法确定工具使用故障源自何处，或故障如何通过调用传播。我们引入了ToolRobustBench，一个用于工具调用代理的分阶段诊断基准，其中工具调用代理是一个LLM系统，它选择工具、提供结构化参数，并解释其返回的反馈。ToolRobustBench将四个扰动家族与工具使用流程对齐：工具接口、用户意图、工具输出/观察以及运行时环境扰动。它将故障归因于工具选择、模式接地、参数绑定、工具输出/运行时反馈处理以及端到端任务成功。在7个模型、16个采样本地工具、4个扰动家族和14个子类型的15,456个单家族实例上进行的实验显示，干净的性能高但不均匀，且鲁棒性显著下降，其中工具输出/观察扰动是主要瓶颈。混合家族实验揭示了非加性故障模式，这些模式无法用孤立的单家族结果解释。因此，ToolRobustBench为诊断超越干净工具调用准确性的鲁棒性提供了一个确定性的、级联感知的基准；

## Abstract
Large language models (LLMs) rely on tool calling as a fundamental agent capability, enabling them to invoke external systems and complete tasks beyond text generation. However, clean end-to-end (E2E) success cannot identify where a tool-use failure originates or how it propagates through a call. We introduce ToolRobustBench, a stage-wise diagnostic benchmark for tool-calling agents, where a tool-calling agent is an LLM system that selects a tool, supplies structured arguments, and interprets its returned feedback. ToolRobustBench aligns four perturbation families with the tool-use pipeline: tool-interface, user-intent, tool-output/observation, and runtime-environment perturbations. It attributes failures to tool selection, schema grounding, argument binding, tool-output/runtime-feedback handling, and E2E task success. Experiments on 15,456 single-family instances across 7 models, 16 sampled local tools, 4 perturbation families, and 14 subtypes show high but non-uniform clean performance and substantial robustness degradation, with tool-output/observation perturbation the dominant bottleneck. Mixed-family experiments reveal non-additive failure patterns that are not explained by isolated single-family results. Thus, ToolRobustBench provides a deterministic and cascade-aware benchmark for diagnosing robustness beyond clean tool-calling accuracy;

## 1. 核心问题与整体含义

- **背景**：大语言模型（LLM）日益依赖工具调用（Tool Calling）作为与外部系统交互的核心机制。工具调用并非简单的问答，而是包含一系列决策：推断用户意图、选择合适的工具、将请求绑定为结构化参数、解释返回结果或执行反馈。这些环节在现实部署中都可能被干扰，例如工具名称被替换为半透明服务标识、相似工具描述重叠、请求表达间接或自相矛盾、返回反馈中出现模式漂移、证据缺失或运行故障。
- **核心问题**：现有评测主要依赖干净环境下的端到端（E2E）成功率，但无法回答两个关键问题：**失败源于哪个阶段**？**错误如何在调用链条中传播**？仅记录最终失败标签会混淆不同能力缺陷——例如，一个"参数错误"症状可能直接来自参数绑定阶段，也可能是工具选择阶段受模糊接口误导后的下游表现。
- **整体含义**：论文主张工具使用评测应同时结合干净成功率、分阶段定位的扰动、以及级联感知（cascade-aware）的错误归因，以提供可复现、可定位的鲁棒性诊断，而非仅一个排名分数。

## 2. 方法论

### 2.1 实例形式化
- 每个实例表示为 `I = (x, R, t*, a*, o*, y*, p)`，其中：
  - `x` 为用户请求，`R` 为候选工具注册表（每个工具包含名称、自然语言描述、JSON Schema、确定性执行器和输出格式）
  - `t*` 为预期目标工具，`a*` 为预期结构化参数，`o*` 为确定性工具输出，`y*` 为预期最终结果
  - `p` 记录扰动家族、子类型和严重程度
- 实例级成功为二元值：模型需同时满足工具选择正确、Schema 合法、参数匹配、执行输出符合预期、最终结果正确，才算成功。

### 2.2 五个诊断能力轴（S1–S5）
| 阶段 | 名称 | 目标能力 |
|---|---|---|
| S1 | 工具选择 | 从候选中选出正确工具 |
| S2 | Schema 接地 | 理解工具名称、描述和 Schema |
| S3 | 参数绑定 | 将用户意图绑定到参数 |
| S4 | 工具输出/运行时反馈处理 | 解释工具返回和运行时反馈 |
| S5 | 端到端任务成功 | 最终任务是否完成 |

这些轴主要用于归因而非完整执行轨迹追踪。

### 2.3 四类阶段对齐扰动家族（14个子类型）
- **家族A（工具接口扰动）**：A1 名称表面替换、A2 描述抽象化、A3 兄弟工具混淆性
- **家族B（用户意图扰动）**：B1 间接表达、B2 欠定规格、B3 干扰上下文、B4 内部冲突
- **家族C（工具输出/观察扰动）**：C1 返回结构噪声、C2 证据丢失、C3 证据污染、C4 证据竞争
- **家族D（运行时环境扰动）**：D1 可用性故障、D2 运行时变异性、D3 反馈质量
- 严重程度分为 light、medium、heavy 三档，通过算子强度静态分数叠加实现，并经过预检门（preflight gate）确保单调性。

### 2.4 级联感知错误归因
- 记录六个诊断字段：观察错误标签、主要错误标签、最早失败阶段、错误源阶段、级联指示器、边界违反指示器。
- **归因逻辑**（确定性回溯，无 LLM 裁判）：
  1. 通过固定优先级（调用存在性 → 格式合法性 → 工具名称解析 → 规范工具匹配 → 必需参数存在 → 参数值匹配 → 执行/后执行成功）得到观察错误标签
  2. 将观察标签与期望的主要失败类型及允许的下游溢出类型比对
  3. 若是允许的溢出，则回溯到最早兼容的上游阶段，记为原始错误源头
  4. 仅当归因源既不在期望主集也不在允许溢出集时，才标记边界违反。

### 2.5 指标定义
- **Clean(m)**：干净实例成功率
- **Robust_f(m)**：家族 f 在三个严重度上的平均成功率
- **Drop_f(m) = Clean(m) − Robust_f(m)**
- **级联率（CR）** 与 **边界违反率（BVR）**：在失败实例上计算
- **混合家族指标**：Δ = 混合成功率 − 较弱组成家族成功率（负值表示混合扰动更难）

## 3. 实验设计

### 3.1 数据与基准
- **工具环境**：40 个确定性本地工具，覆盖 12 个功能组（天气/环境、转换、检索、路线/时间、列表、日历、邮件、文件、电商、CRM/工单、数据库、安全）；主实验用固定种子采样 16 个工具。
- **数据构建**：手工编写的请求模板填充具体参数值生成干净锚点；所有锚点经确定性执行器验证后才用作扰动锚点。GPT 仅用于提示模板多样化起草，最终数据由确定性代码生成。
- **数据规模**：完整单家族评测共 **15,456 条模型输出记录**（7 模型 × [4 家族 × 48 干净基线 + 14 子类型 × 3 严重度 × 48]），包含 1,344 条干净基线和 14,112 条扰动记录。

### 3.2 评估模型

## 6. 主要结论与发现

1. **干净性能高但不均匀，鲁棒性远未解决**：平均干净成功率 0.979，三个模型达到 1.000，但扰动下总体鲁棒性仅 0.664–0.766。任务级差异显著（filter_items 仅 0.881，而多个工具达 1.000）。
2. **工具输出/观察扰动是主要瓶颈**：家族 C 平均成功率仅 0.455，无模型超过 0.60；接口扰动最轻（0.918），用户意图（0.773）和运行时环境（0.688）居中。
3. **C2 证据丢失最难，且失败并非因目标不可恢复**：C2 平均成功率仅 0.142；人类可恢复率 YES+PARTIAL 达 68.3%，而最优模型成功率仅 27.8%，说明这是模型短板而非任务缺陷。
4. **级联归因有效区分下游症状与上游原因**：运行时环境扰动级联率最高（0.638），接口扰动 0.352，而 C 族仅 0.003；反事实修复中 72.4% 的失败在修复主要错误后可恢复。
5. **混合扰动呈非加性失败模式**：medium 下混合成功率 0.448 vs 较弱组成 0.621 vs 两者均值 0.754；A3+C4 和 B4+C4 交互破坏性最强。
6. **诊断标签可指导有针对性的干预**：B 族 S3 参数绑定提示无效（21/30→21/30），证实了 S1 根源诊断；A 族提供别名后从 21/30 提升到 30/30，验证了 S1 修复有效性。

## 7. 优点

- **阶段对齐的扰动分类学**：四类扰动精确对应工具调用管线的不同入口点，使失败定位具有结构性解释力。
- **级联感知归因机制**：将观察标签与主要标签分离，通过确定性回溯区分症状与根源，且归因过程无 LLM 裁判，保证可复现性。
- **确定性可复现评测**：40 个确定性本地工具、稳定金标参数与预期结果，避免实时 API 波动，全部主要结果可从原始记录重新计算。
- **多重验证证据链**：可恢复性审计、反事实归因、定向干预实验、人类审计从不同角度验证了诊断标签的有效性与实用性。
- **对现有评测的补充定位明确**：与轨迹级归因（Who&When）、多级鲁棒性（RoTBench）、真实噪声（AgentNoiseBench）存在清晰互补关系。

## 8. 不足与局限

- **受控环境的覆盖限制**：确定性本地工具无法代表真实 API 生态的认证、限流、有状态副作用、供应商特定错误语义和长时程依赖。
- **单步任务范围**：不测试长时程规划、持久状态或多工具依赖链。
- **混合家族覆盖不完整**：仅报告 5 对代表性组合；部分组合（如 C–D）因归因目标模糊被排除；部分混合出现正 Δ（如 A2+B3 重严重度）可能来自地板效应或模板差异而非真正的鲁棒性提升。
- **严重度不保证经验单调性**：更显式或更严重的运行时故障有时反而更容易分类，严重度仅作为输入侧受控应力轴。
- **协议兼容性残余变异**：模型通过不同后端访问，无法完全排除协议差异对结果的影响。
- **人工审计样本偏差**：审计样本刻意覆盖大量重度和失败案例，不能作为全基准模糊/困难案例的无偏估计；注释协议允许"不清楚"判定，会减少某些一致性指标的有效样本量。
- **算力与成本信息缺失**：未报告任何训练/推理资源使用情况，难以评估复现成本。
