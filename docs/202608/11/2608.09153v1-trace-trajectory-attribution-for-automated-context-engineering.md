## 摘要
生产环境中的AI智能体在其上下文来源——系统提示、知识库、工具描述和程序化技能——包含错误或缺口时会发生故障。当前的维护依赖于人工日志审查和临时调试，随着交互量的增长，这造成了可扩展性瓶颈。我们提出了TRACE（面向自动化上下文工程的轨迹归因），一种自动化的反馈循环，通过挖掘历史智能体轨迹来诊断和修复上下文故障。我们的关键洞见在于，轨迹中蕴含着丰富的隐性不满信号——用户纠正、重新措辞、放弃线索——这些信号无需显式反馈收集，就能精确揭示上下文来源在何处失效。与模型微调不同，TRACE作用于上下文层，无需重新训练即可实现快速迭代。我们做出了四项贡献：（1）一种轨迹挖掘框架，从历史智能体执行中系统性地提取诊断信息；（2）多组件因果归因，将文本梯度从单体提示优化扩展到异构上下文来源（技能、知识库、工具、提示）；（3）探索性验证，智能体主动阅读上下文来源，以区分需要CREATE的内容缺口与需要UPDATE的过时内容，实现了96%的操作准确率；（4）一种可复用的仿真方法和可验证基准，以解决上下文调试缺乏开放数据集的问题，包含六类故障分类法、真实标注和跨层验证协议。在跨越三个复杂度层级（最多16个执行节点）的60条不满轨迹上，TRACE实现了72.7%的根因归因准确率和82%的端到端修复有效性，表明通过挖掘历史轨迹（生产系统中一个被忽视的资源），超过80%的上下文层故障可以被自动诊断和修复。

## Abstract
Production AI agents fail when their context sources -- system prompts, knowledge bases, tool descriptions, and procedural skills -- contain errors or gaps. Current maintenance relies on manual log review and ad-hoc debugging, creating a scalability bottleneck as interaction volume grows.   We present TRACE (TRajectory Attribution for Automated Context Engineering), an automated feedback loop that mines historical agent trajectories to diagnose and remediate context failures. Our key insight is that trajectories are rich with implicit dissatisfaction signals -- user corrections, rephrasing, abandonment cues -- that reveal precisely where context sources failed, without explicit feedback collection. Unlike model fine-tuning, TRACE operates on the context layer, enabling rapid iteration without retraining.   We make four contributions: (1) a trajectory mining framework that systematically extracts diagnostic information from historical agent executions; (2) multi-component causal attribution that extends textual gradients from monolithic prompt optimization to heterogeneous context sources (skills, knowledge bases, tools, prompts); (3) exploratory verification, where agents actively read context sources to distinguish content gaps requiring CREATE from stale content requiring UPDATE, achieving 96% operation accuracy; and (4) a reusable simulation methodology and verifiable benchmark addressing the absence of open datasets for context debugging, with a six-category fault taxonomy, ground truth annotations, and a cross-layer verification protocol.   On 60 dissatisfaction traces spanning three complexity tiers (up to 16 execution nodes), TRACE achieves 72.7% root cause attribution and 82% end-to-end fix effectiveness, showing that over 80% of context-layer failures can be automatically diagnosed and remediated by mining historical trajectories, an overlooked resource in production systems.

- 现有维护方式依赖人工审查日志、临时错误报告和定期审计，导致两个核心问题：
  - **可扩展性瓶颈**：随着交互量增长，故障发生到修复之间的时间差距越来越大，用户不满不断累积。
  - **诊断困难**：故障的表象（如用户失望、工具错误）往往与其根因（某个上下文源中的内容问题）相距甚远。
- 论文的核心洞见是：历史代理轨迹中蕴含着大量**隐式不满信号**（用户纠正、重新措辞、放弃线索等），这些信号无需显式收集反馈或人工标注，即可定位上下文源的失效位置。DRIFT 等已有工作证明这类隐式信号出现频率约为显式满意信号的两倍，且信息更丰富。
- TRACE 的定位是**不修改模型权重**，只操作“上下文层”，从而在无需重新训练的情况下实现快速修复迭代。

## 2. 方法论：核心思想、关键技术细节与流程

### 2.1 整体架构
- TRACE 是一个自动反馈闭环，包含三个专用代理（Agent）：
  1. **Detector（检测器）**：从轨迹中识别显式（如工具错误、明确降级反馈、放弃会话）和隐式（如会话修复、重复提问、负面情绪、语义漂移）的 DSAT 信号，输出二元判定与置信度。
  2. **Root Cause（根因代理）**：将轨迹建模为上下文计算图，通过 **delta（损失信号）** 引导的 **整体归因（Holistic Attribution）**，在单个 LLM 调用中反向遍历轨迹，定位最早引入错误的节点，并生成文本梯度。
  3. **Recommender（推荐代理）**：不被动接受根因分析，而是**主动探索**上下文源文件（读取知识库、技能文件、系统提示等），验证假设，区分内容缺失（CREATE）与内容过时（UPDATE），生成 CRUD 建议供人工审查。
- 最终修复结果由人工审批后，反馈到上下文工程范围（系统提示、工具提示、知识库、知识图谱、技能文件）。

### 2.2 关键技术细节
- **轨迹作为计算图**：将对话轨迹定义为 \( G = (V, E) \)，每个节点代表决策点（如技能查询、KB 搜索、数据库查询、响应生成），并记录内容 \( c_v \) 与输出 \( o_v \)。
- **Delta 引导的整体归因**（Algorithm 1）：
  - 从用户纠正和代理响应中提取 delta（例如“期望 X，但得到 Y”）作为损失信号。
  - 将轨迹节点按时间倒序排列，在一个 LLM 调用中完成反向遍历。
  - 关键判断逻辑：**最早输出包含 delta 但输入不含 delta 的节点引入了错误**，后续节点仅传播错误。
  - 与迭代式逐节点归因相比，单次调用减少 LLM 调用量约 16 倍，且避免了上下文截断损失。
- **文本梯度**：借鉴 TextGrad 的概念，为每个节点生成自然语言的“梯度”描述，包括归因分数、具体修改建议和因果依据。
- **探索性验证**：Recommender 会执行多阶段探索：读取被归因组件、搜索权威来源（如政策文档）、交叉引用验证、探索相关组件，并基于四维诊断（存在性、可访问性、正确性、一致性）来生成操作类型。
- **仿真数据生成**：提出三层生成架构（上下文源 → 故障定义 → 执行轨迹），并用五步验证协议确保地面真值完整性和可复现性。

## 3. 实验设计：数据集、基准与对比方法

### 3.1 数据集 / 场景
- 由于无法使用真实生产数据（保密约束）且没有现成基准，作者构建了**合成数据集**。
- 数据集包含 **75 条轨迹**：
  - 60 条含不满信号（DSAT）轨迹，有已知根因；
  - 15 条控制轨迹（成功交互），作为阴性样本。
- DSAT 轨迹覆盖 **3 个复杂度层级**：
  - 简单：2–8 节点（36 条）；
  - 复杂：9–11 节点（14 条）；
  - 困难：15–16 节点（10 条）。
- 故障类别 **6 类**：
  - SKILL_FILE_STALE（12）：技能流程过时；
  - KB_CONTENT_STALE（12）：知识库内容过时；
  - KB_CONTENT_GAP（11）：知识库内容缺失；
  - TOOL_PROMPT_ERROR（9）：工具提示错误；
  - SYSTEM_PROMPT_GAP（6）：系统提示缺少行为指令；
  - RETRIEVAL_FAILURE（10）：检索失败（同义词/缩写不匹配）。
- 使用的工作示例为**金融运营场景**（发票审批、采购政策更新），每个轨迹都有完整的地面真值：根因节点 ID、组件路径、预期归因分数、预期 CRUD 操作。

### 3.2 Benchmark
- 作者构建了“可验证上下文调试数据集”（Verifiable Context Debugging Dataset），包含 23 个上下文源文件、75 条轨迹、每条轨迹带精确地面真值，并通过五步验证协议（工具输出与源文件一致、故障标注存在、交叉引用完整、根因节点正确、归因分数和为 1）确保数据完整性。

- **不足与风险**：
  - 样本量较小（60 条 DSAT），95% 置信区间较宽（例如节点准确率区间 [59%, 85%]），统计功效有限；
  - 合成数据虽设计良好，但可能无法完全代表真实生产轨迹的复杂噪声（如混合话题、多轮长会话、异常模式）；
  - Detector 实验显示 vanilla LLM 已是满分，削弱了结构化信号分类法的相对价值；
  - 根因归因对工具（66.7%）和 KB（83.3%）的准确率较低，说明困难类别仍需改进；
  - 与迭代基线的对比仅用 10 条复杂轨迹，规模较小；
  - 没有跨领域验证（仅金融运营场景）；没有与真实人工标注的对照。

## 6. 主要结论与发现

- **端到端有效性**：TRACE 在 60 条不满轨迹上取得：
  - 根因节点准确率（Acc@1）：72.7%；
  - 端到端修复有效性（正确操作 + 正确路径）：82%；
  - CRUD 操作准确率：96%；
  - 路径准确率：82%。
- **探索性验证的重要性**：对于知识库内容故障（GAP vs STALE 区分），主动探索将操作准确率从 33% 提升到 83%；当根因归因错误时，探索机制仍能以 67% 的概率生成正确修复建议。
- **整体归因优于迭代**：在复杂轨迹上，整体归因准确率是迭代方法的 2 倍（40% vs 20%），且 LLM 调用次数少约 16 倍。
- **历史轨迹的挖掘价值**：作者主张，超过 80% 的上下文层故障可通过挖掘历史代理轨迹来自动诊断和修复，而这一资源在现有生产系统中常被忽视。
- **检测器结论**：现代基础模型本身已具备强大的二元 DSAT 识别能力，结构化的信号分类法不带来准确率提升，但会提供更丰富的诊断信息。

## 7. 优点

- **问题定位新颖且实用**：将“隐式不满信号”“上下文计算图”“文本梯度”相结合，直接解决上下文调试的可扩展性问题，而不是简单做模型微调。
- **不依赖人工标注**：通过挖掘已有轨迹中的隐式信号，避免了昂贵的显式反馈收集。
- **整体归因设计高效**：单 LLM 调用实现反向归因，既节约成本，又避免了迭代方法无法区分“引入错误”和“传播错误”的短板。
- **探索性验证的引入**：Recommender 主动阅读上下文文件，而不是被动接受根因结果，是架构上的关键创新，且用消融实验证明其必要性。
- **提供了可复用的仿真方法论**：由于缺乏开放基准，作者将合成数据生成方法（三层架构、故障定义、验证协议）作为贡献，方便其他团队生成领域特定测试集。
- **实验体系完整**：从单组件评估到端到端评估、从消融到完整案例（附录 K），呈现了较清晰的验证链条。
- **写作与透明性**：附录提供了详细提示模板、算法伪代码、指标定义和验证脚本，可复现性强。

## 8. 不足与局限

- **实验规模小、置信区间宽**：60 条 DSAT 轨迹和最多 10 条消融轨迹在统计上偏弱，部分区间下限较低（节点准确率 59%），结论的稳健性受限。
- **合成数据的外推风险**：虽然仿真设计刻意追求真实性（金融数值、政策日期、人员行为），但合成轨迹无法涵盖真实生产数据中的话题漂移、长对话结构和多模态交互，可能高估系统在实际部署中的表现。
- **检测器部分存在冗余性**：实验表明 vanilla LLM 已达到完美 F1，说明 TRACE 的单层结构并未带来精确检测优势，仅提供了额外诊断字段（证据、信号类型等），价值未被直接量化。
- **根因归因在困难类别上明显偏低**：工具类（66.7%）和知识库类（83.3%）的准确率较低，且检索失败等类别没有给出独立准确率，可能掩盖了系统对特定故障类型的弱点。
- **路径准确率不高**：82% 意味着约五分之一的情况无法准确定位需要修改的文件，这在生产落地中可能导致人工仍需从头排查。
- **缺乏真实生产验证**：出于保密，没有在真实企业系统上公开评估，也没有与人工调试生产效率的对照组。
- **资源消耗未披露**：全文未提及计算资源（GPU、时间、成本），无法评估部署成本。
- **普适性存疑**：仅使用金融运营领域的一个场景，未讨论如何迁移到医疗、法律、客服等其他领域的上下文源结构，系统对各领域特定故障类型的覆盖未知。
- **负例设计较简单**：15 条控制轨迹全部为成功交互，未包含“无故障但用户不满”的噪声场景，可能高估 Detector 的实用性。
