## 摘要
工具增强型语言模型代理在外部系统上执行多步骤工作流，先解析一次实体，然后在后续步骤中对其进行操作。先前研究表明，在单步操作中，代理选择正确工具但将其绑定到错误实体的概率为24-26%。我们研究实体绑定随时间的变化：它们是保持正确、悄无声息地漂移到不同实体，还是如果最初就是错误的，则传播并加剧？我们将绑定漂移（步骤1正确，之后错误）与错误传播（步骤1错误，持续传递）区分开来，并在不相交的工作流集上对它们进行评分，以避免两者混淆。在一个受控的多步骤测试平台（200个工作流，580个实体绑定评分步骤，四个企业领域，八个从小型到前沿的模型后端）中，我们发现：(1) 在受控错误注入下，实体锁定（直观的“持久化首次绑定”修复方法）将错误操作从907个放大到2,746个（3.0倍；自助法95%置信区间[2.8, 3.3]），因为它忠实地将注入的错误实体带入每个后续步骤；(2) 受影响最大的模型（Claude Opus 4.5）上的放大倍数达到8.5倍；(3) 一种实用的基于LLM的重新验证器（一次廉价的小型第二模型调用，重新读取原始指令）将错误操作减少了79%（0.21倍；置信区间[0.18, 0.25]），将差距缩小到与Oracle上界（0.20倍）相差1个百分点以内；(4) 在自然（非注入）环境中，基线代理在18%的合格工作流上发生漂移，且每步错误率随步骤增加而上升。持久化和重新验证不可互换：一种消除漂移的防御措施可能加剧传播，而一种实用的重新验证器几乎可以媲美Oracle恢复。

## Abstract
Tool-augmented language-model agents execute multi-step workflows over external systems, resolving an entity once and then acting on it across subsequent steps. Prior work shows that in single-step actions, agents select the correct tool but bind it to the wrong entity 24-26% of the time. We study what happens to entity bindings over time: do they stay correct, silently drift to a different entity, or, if wrong from the start, propagate and compound? We formalize binding drift (correct at step 1, wrong later) as distinct from error propagation (wrong at step 1, carried forward), and score them on disjoint workflow sets so the two cannot be conflated. In a controlled multi-step testbed (200 workflows, 580 entity-binding-scored steps, four enterprise domains, eight model backends spanning small to frontier), we find: (1) under controlled error injection, an entity lock (the intuitive "persist the first binding" fix) amplifies wrong actions from 907 to 2,746 (3.0x; bootstrap 95% CI [2.8, 3.3]), because it faithfully carries the seeded wrong entity into every later step; (2) the amplification reaches 8.5x on the most affected model (Claude Opus 4.5); (3) a practical LLM-based re-verifier (a single cheap second model call re-reading the original instruction) reduces wrong actions by 79% (0.21x; CI [0.18, 0.25]), closing the gap to within 1 percentage point of an oracle upper-bound (0.20x); and (4) in the natural (non-injected) setting, baseline agents drift on 18% of eligible workflows, with the per-step error rate rising across steps. Persistence and re-verification are not interchangeable: a defense that eliminates drift can worsen propagation, and a practical re-verifier nearly matches oracle recovery.

# 论文详细总结：《Binding Drift in Multi-Step Tool-Augmented Agents》

## 1. 核心问题与整体含义（研究动机和背景）
- **研究动机**：工具增强型语言模型代理在执行多步骤工作流时，通常需要先解析一个实体（如账户、事件），然后在后续步骤中持续对其进行操作（如“添加备注”“更新日期”“发送邮件”）。单步动作中，代理选对工具但绑定错实体的错误率已有研究（24-26%）；但**随时间推移，绑定状态会如何变化**——是否保持正确、悄然漂移到另一个实体、或从一开始就错误并传播放大——尚未被系统研究。
- **核心问题**：区分两种本质不同的多步故障模式：
  - **绑定漂移（Binding Drift）**：步骤1绑定正确，后续某步骤却静默地绑定到另一个有效实体（如代词重新解析、同名称干扰项突出、早期解析超出上下文）。
  - **错误传播（Error Propagation）**：步骤1绑定错误，然后该错误被持续携带到所有后续步骤。
- **整体含义**：漂移和传播是不同的故障，需要不同的防御策略。简单的“解析一次，一直用”（实体锁定）能消除漂移，但会放大传播；而重新推导（re-derivation）则可以同时应对两者。该工作为多步代理实体跟踪提供了形式化度量和实用修复方案。

## 2. 方法论：核心思想、关键技术细节
### 核心思想
- **形式化分离**：将漂移和传播定义在不相交的工作流集合上——漂移只评估在步骤1绑定正确的工作流，传播只评估在步骤1绑定错误的工作流。这样，一个指标改善不会以牺牲另一个为代价。
- **受控错误注入**：为了大规模测量传播而不依赖模型自然错误率，在步骤1之前向代理的状态和历史中注入一个已知错误的实体绑定，如同故障注入测试。
- **防御策略**：
  - **实体锁定（Entity Lock）**：固定第一次绑定的实体ID，后续步骤直接重用——直觉上防止漂移。
  - **LLM自/交叉重验证**：在每次动作步骤后，用同一模型或小模型（Nova Micro）做一次独立的实体解析，若与携带的绑定不一致则覆盖。
  - **Oracle重验证**：使用真实情况解析器重新推导——作为性能上界。
- **漂移模式分类**：定义了5种压力模式（D1-D5），分别对应不同机制（时间重复、干扰项注入、依赖链、真正歧义、静默切换）。

### 关键技术细节
- **绑定状态图（Binding-State Map）**：记录每个步骤每个语义槽的正确实体，区分主携带槽和派生槽（通过关系如 `owner-of` 得到）。
- **评分条件**：只当代理选择了正确的工具时才评分绑定正确性，从而分离工具选择错误和绑定错误。
- **指标**：
  - 漂移、传播、恢复（工作流级二值指标）。
  - 每步错误实体率、复合因子、过度澄清率、工作流成功率。
- **注入协议**：在步骤1前添加先验回合“（先前）将[槽]识别为[错误ID]”，若启用锁定则预设锁定为错误ID。

## 3. 实验设计
### 数据集/场景
- **基准（Benchmark）**：200个合成工作流（总890步，其中580步参与实体绑定评分），覆盖4个企业领域（日历、CRM、文档、工单），每个工作流3-5步。
- **5种漂移模式**（各40个工作流）：
  - D1 时间重复（日历上多个同名事件）
  - D2 干扰项注入（同名实体增强元数据出现在中间）
  - D3 依赖链（引用前一步解析的实体，跨域）
  - D4 真正歧义（无消除歧义信息，正确行为是澄清）
  - D5 静默切换（三个同名实体，限定词在步骤1后消失）

### 对比方法
- **防御配置**（5种）：
  - 基线（无防御）
  - 实体锁定
  - LLM自重验证（同一模型）
  - LLM交叉重验证（使用Nova Micro作为验证器）
  - Oracle重验证（上界）
- 额外在自然模式下评估了“持久化栈”（锁定+出处检查点+漂移感知门）。
- **模型**：8个后端（Amazon Nova Micro、Llama-3.1-8B、Nova 2 Lite、Claude Haiku 4.5、Llama-3.3-70B、Nova Premier、Claude Sonnet 4.5、Claude Opus 4.5）。

### 实验条件
- **自然模式**：代理自行解析每一步。
- **注入模式**：在160个非歧义工作流上注入已知错误绑定（每个模型×5防御配置，共约1280个工作流×配置）。

- **实验数量**：主实验中，注入模式下每防御配置处理1,280个合格工作流（8模型×160非歧义工作流），自然模式监控所有200工作流。加上离线验证（25个断言全部通过），整体实验量充足。
- **充分性与公平性**：
  - 跨模型（小型至前沿）测试，消除单一模型偏差。
  - 结合自然和注入模式，既能测量自然漂移率，又能解耦传播测量。
  - 采用自助法95%置信区间报告核心结果。
  - 消融实验：比较锁定、重验证、Oracle、持久化栈，揭示不同防御的权衡（漂移 vs 传播）。
- **潜在偏差**：所有数据为合成数据；注入协议仅使用单一措辞；提示词中命令代理“不得静默切换”，可能影响锁定遵从度。

## 6. 主要结论与发现
1. **实体锁定放大传播**：注入条件下，错误操作从基线907个增至2,746个，放大3.0倍（95% CI [2.8, 3.3]）；在Claude Opus 4.5上达到8.5倍。
2. **LLM交叉重验证近乎Oracle**：用廉价小模型（Nova Micro）做重验证，错误操作降至189（0.21倍，CI [0.18,0.25]），仅比Oracle（180, 0.20倍）高1个百分点。
3. **自然模式下漂移明显**：基线代理在18%的合格工作流上发生漂移，每步错误率从~8%（1-2步）升至28%（第3步），而锁定将其压平至9%以下。
4. **漂移和传播对同一防御响应相反**：锁定消除漂移但放大传播，强调二者不能混为一谈。
5. **过度澄清-安全性权衡**：所有防御以增加澄清为代价减少错误动作；Oracle将澄清从743增至2,400次。

## 7. 优点（方法/实验设计亮点）
- **形式化区分**：首次在代理轨迹层面严格定义并独立测量绑定漂移和错误传播，避免了指标混淆。
- **受控错误注入**：借鉴故障注入，使传播测量与模型自然错误率解耦，可用于任何模型。
- **实用修复方案**：LLM交叉重验证简单接入（一次API调用）、近乎达到Oracle上界，提供可立即部署的防护。
- **多维评价**：不仅报告错误减少，还报告过度澄清率、工作流成功率，全面揭示权衡。
- **跨模型覆盖**：8个模型（从0.5B到前沿）提供鲁棒性。

## 8. 不足与局限
- **生态效度**：工作流仅3-8步，合成实体库；真实企业工作流（15-50步、噪音记录、并发状态变化、多提供方）可能呈现不同动态。
- **覆盖范围有限**：最多只测试了一个派生槽（D3模式）；更丰富的级联未验证。
- **注入方案简化**：使用单一措辞、固定注入位置（步骤1）；更逐渐的腐化模式（过期记录、冲突元数据）未建模；系统提示词可能高估锁定遵从性。
- **统计局限**：仅报告自助法置信区间，无正式假设检验；聚合值可能掩盖模型间1.8-8.5倍的差异；工作流内部结构模板相似，降低独立性。
- **构造定义**：漂移标记未区分静默重新解析和上下文遗忘；将注入状态冲突下的澄清标记为“过度澄清”可能过于严苛。
